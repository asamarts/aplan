# TUI user guide

`aplan tui` is the interactive view and control surface for the same plan, diagnostics, graph,
evidence and guarded mutations as the CLI. It does not maintain a second plan or relax a gate.
Every screen either presents a typed application result or prepares the same mutation that its
named CLI command would perform.

![A check-to-fix and evidence-gated close in the real TUI](demos/tui-work-loop.gif)

The recording is generated by [`demos/tui-work-loop.tape`](demos/tui-work-loop.tape) from a real
default-feature build and the tracked safe fixture. It first fixes a reported `APLAN009`, then
finds and reviews `Close task with evidence` through the action palette before publishing it.

## Install and launch

The standard binary includes the TUI. A source build uses the default `tui` Cargo feature:

```sh
cargo build --release
target/release/aplan facts --require build.tui
target/release/aplan tui
```

The explicit headless shape is `cargo build --release --no-default-features`. It omits
`aplan-tui`, Ratatui and Crossterm, but keeps an `aplan tui` enablement stub so command discovery
does not depend on the build shape. Release automation enables the `tui` feature explicitly.

Launch from a repository containing `.aplan.yml`, or select the session inputs exactly:

```sh
aplan tui --root plan
aplan tui --config /trusted/policy.yml --root checkout/plan
aplan tui --no-config --root checkout/plan
```

`--config` and `--no-config` are trust decisions. The loaded plan root, configuration source and
repository identity stay visible and fixed for that session. Both standard input and standard
output must be terminals; redirected use is served by the ordinary CLI and its machine formats.

### If no plan can be loaded

Missing configuration, a missing plan, a missing root, unreadable input and invalid configuration
open distinct onboarding states. The screen says what was searched and shows an exact quoted
repair or non-overwriting `aplan init` command. It never runs that command itself. Make the repair
in another shell, then press `r` to retry, or quit and relaunch with the displayed `--root`,
`--config` or `--no-config` choice. Press `i` to inspect the build and capabilities even when no
plan is loaded.

## The work loop

The six destinations answer different questions:

1. **Overview**: Is the loaded plan healthy, and where should attention go next? Counts and meters
   open the exact tasks or cuts behind them.
2. **Tasks**: What is true about one work item, why can or cannot it start, and what may be done to
   it? The inspector keeps summary, work, body, relations, paths, traces and evidence separate.
3. **Diagnostics**: What did the complete structural or configured-document check find? Search and
   filters narrow presentation, never the run whose PASS/WARN/DENIED verdict remains in the title.
4. **Graph**: How does work depend on other work, at plan, phase, milestone and task levels?
5. **Reports**: What aggregate or historical signal needs a planning decision? Roadmap, version,
   stale work, path specificity, vacuity, deprecation and summary reports live here.
6. **Inbox**: Which retained intake needs review? Search and structured filters distinguish open,
   deferred, promoted and discarded captures; the inspector retains absolute times, kind/profile,
   source provenance, promotion defaults, disposition and the promoted-task link.

Use `1` through `6` to change destination, arrows or `j`/`k` to move, `Tab` and `Shift-Tab` to
change the focused region, `Enter` to open, and `Esc` to reverse one layer. `q`, base-shell `Esc`
and `Ctrl-C` quit safely. Mouse input is an optional accelerator; no workflow requires it.

The complete generated binding and action table is in
[`tui-reference.md`](tui-reference.md). It is derived from the same closed catalogues as dispatch,
contextual help and the command palette; the specification gate rejects a stale file.

### Search, filters, help and actions

- `/` searches entities within the current destination. It never changes structural scope.
- `f` edits structured filters. Active constraints stay visible and can be cleared with `x`.
- `?` shows the actions in the current context, including why an action is unavailable.
- `Ctrl-P` searches every shell action, all guarded mutations and every deliberate CLI-only
  boundary. Search accepts action titles and the corresponding CLI names.
- `r` refreshes the identified input. A failed or stale refresh does not replace the last complete
  snapshot.
- `i` shows the exact build, source and capability identity.
- `Ctrl-N` opens Quick capture globally and returns to the same destination after a successful
  identity-confirmed reload.

Text typed into a focused field is text: `/`, `?`, `q`, `r` and destination numbers do not escape
the form. `Enter` in a text field never confirms. Mutation confirmation needs a newly pressed key
while the labelled control has focus; key repeat and paste cannot publish a change.

## Diagnostics and verification

Diagnostics retains the complete run and then lets you search, group or filter its findings. A
zero-row filtered view therefore repeats the complete verdict instead of calling itself clean.
Open a finding to see its stable rule, subject, location, exact message, agent instruction, safe
source context and task link. `e` explains the selected rule and `E` finds a rule code directly.
`a` prepares one structural-check override for one run; an ordinary refresh returns to repository
policy.

`V` opens the evidence-verification run sheet. Review the selected repository and configuration,
effective evidence policy and any configured command boundary before choosing resolve-only or
test execution. Verification runs on the bounded worker while already loaded views remain usable.
Late, stale, timed-out, output-limited, unavailable and failed answers are distinguished; none can
appear as resolved. Exact repairs, when present, are offered through the separately reviewed
`Apply verification repairs` mutation.

## Guarded mutations

Open a task or search `Ctrl-P` for coordination, planning, authoring and evidence actions. The TUI
contains the complete native mutation catalogue: claim/release, start/stop, dependency and
preference edits, tags, move/drop, add/import, supersede/rekey, close/amend/restamp and exact
verification repairs.

The common sequence is:

1. fill the typed form, whose required, optional and derived values are labelled;
2. request a preview, which runs the same whole post-state validation as the CLI;
3. inspect the exact affected tasks, files, findings and before/after bytes;
4. deliberately focus Confirm and press a fresh key; and
5. wait for an identity-confirmed reload before treating the result as committed.

The word `COMMITTED` means the reloaded application snapshot contains every reviewed after-state.
`RELOAD REQUIRED`, `PARTIAL` and `DIVERGED` are different outcomes with recovery instructions; do
not blindly retry a broad mutation. Like the CLI, the TUI edits the working tree and never creates
a Git commit.

### Capture and Inbox

`Ctrl-N` opens the shortest intake path from every destination. Title is the only required field;
kind, explicit repository profile, short body, labels and revisit time remain available without
turning the form into task authoring. Paste and Unicode use the same bounded text editor as every
other mutation. A successful capture retains `origin: tui` and leaves the navigation route and
task selection unchanged.

Destination `6` initially shows actionable open captures. Use `/` for id/title/body search and `f`
for state, revisit, kind and label filters; terminal records and deferred open records remain
available rather than disappearing. List and detail views use `OPEN`, `DEFERRED`, `PROMOTED` and
`DISCARDED` text in addition to style. Times are absolute UTC values. Configured kinds and profiles,
opaque-source namespace/key, snapshotted promotion defaults, disposition reason and promoted task
are shown in the inspector when present.

The palette and contextual help expose Amend, Discard, Restore and Promote only for a compatible
selected state and retain a visible reason when another state refuses the action. Every operation
has the ordinary review/recompute/confirm boundary. Promotion takes task placement fields from the
same vocabulary as Add, then publishes the new task and retained capture disposition as one guarded
batch. After reload, `Enter` on a promoted capture opens its loaded task; the capture remains the
durable origin record.

Batch artifacts, alternate repository roots, transport servers and automation-owned receipt
workflows remain explicit CLI boundaries. Selecting one in help or `Ctrl-P` gives the exact
copyable command and reason instead of spawning a shell. The generated
[`action reference`](tui-reference.md#guided-and-cli-only-boundaries) is the authoritative list.

## Explore the graph

Graph is a multiscale dependency explorer, not a table. `Enter` drills from the plan Overview into
a phase, milestone and task; `Esc` reverses that semantic history. Phase is an ordered grouping
band, milestone is the plan's one membership level, and only task dependencies express causality.
Aggregate edges retain the underlying task-edge provenance rather than inventing dependencies
between groups.

Three movements must not be confused:

- **Viewport movement** changes only which cells are visible. Use uppercase `H`, `J`, `K`, `L` to
  pan and `Home` or `0` to recenter on the selected node. It changes no selection or scope.
- **Semantic navigation** changes the selected entity. Arrows or `h`/`l` move through laid-out
  geometry; `[` and `]` visit direct blockers and dependents; `{` and `}` jump dependency layers;
  `^`, `$`, `C`, `M`, `P`, `N` and `!` visit sources, sinks, critical-route nodes, milestones,
  phases and nodes with findings. Enter drills into the selected aggregate or task.
- **Window traversal** changes which bounded source region is admitted. When a graph is larger than
  the work budget, `,` and `.` select an incoming, outgoing, membership, component or paged
  continuation and `n` opens it. Exact visible/admitted/omitted counts and source-bound cursor
  identity prevent one window from looking like the complete graph.

`g` cycles whole, upstream, downstream, between, unreachable, neighbourhood and critical scopes;
the label says whether dependency, membership, all-`blocked_by`, or dependency-plus-containment
relations were walked. `b` supplies the endpoints for a between scope. `f` composes cut, phase,
tag, owner, status and unclaimed filters. `m` toggles cut-membership edges. `o` hides unrelated
edge paint without changing navigation or counts.

Presentation remains separate from scope. `s` changes peer ordering, `d` changes flow direction,
`v` changes card density, `z` fits the origin, and `-`/`+` changes neighbourhood depth. The header
names the current level, scope, direction, order, density, selection, relation position, visible
extent and omission accounting. A filtered or windowed answer never calls itself complete.

Use the CLI when a full static or machine graph is the right answer:

```sh
aplan graph                                      # attended layered scene
aplan graph --format text --width 120            # deterministic redirected scene
aplan graph --format text --width 120 --level phase:2 --order criticality
aplan graph --format text --width 120 --level task:A1-451 --orientation top-to-bottom
aplan graph --format mermaid > graph.mmd          # complete external-layout input
aplan graph --format dot > graph.dot
aplan graph --format json > graph.json
```

A redirected bare `aplan graph` remains Mermaid for compatibility. Explicit `--format` always
wins. Layered text paints a complete admitted scene or reports exact omissions and continuation
guidance; Mermaid, DOT and JSON have no terminal width limit. `--layout lanes` retains the older
row-and-lane text document when byte compatibility matters.

## Loading and long operations

The first owned frame identifies the current phase, such as build identification, input discovery,
plan loading or projection. Bounded work shows exact progress; indeterminate work shows its phase
and elapsed activity without inventing a percentage or ETA. The interface remains responsive,
allows cancellation only where the provider can honor it, and keeps prior complete data visible.
`--reduced-motion` preserves the text state without animation.

Outside the TUI, slow human-format commands show delayed stderr progress only after a 120 ms grace.
Use `--progress never` for an explicit silent programmatic invocation, or `--progress always` to
request stderr progress beside redirected output. Machine formats never gain presentation bytes,
and `CI` suppresses automatic progress. The TUI always owns progress in-frame: its `--progress`
option never writes a second stream outside the screen and does not remove the in-frame state.

## Layout, appearance and accessibility

The shell derives layout from cells, not terminal brand:

- 120x24 and larger can show the destination rail, primary content and detail together;
- 80x18 and larger use tabs with a primary/detail split;
- narrow and short supported layouts route one pane at a time with an explicit breadcrumb/back;
- 48x14 is the supported floor; below it, only current/required size and safe exit/retry guidance
  are shown.

Resize retains destination, selected identity, filters, inspector section, graph anchor/history,
logical scroll and uncommitted form bytes. Long detail wraps by terminal display width; tables use
an explicit continuation or detail route instead of silently clipping truth.

Low-color is the background-neutral default. Select `--theme dark`, `light`, `low-color` or
`monochrome`; `t` cycles themes when allowed. `NO_COLOR` fixes monochrome. `--ascii` selects ASCII
borders and graph tokens on the first frame, while `u` toggles presentation in-session. Status,
selection, focus, graph roles, severity and continuation all retain words, punctuation or text
badges without color. `--reduced-motion` disables activity animation.

The TUI is keyboard complete, provides visible focus, traps focus inside modals, and requires no
mouse gesture. It does **not** claim a screen-reader accessibility tree: alternate-screen cell
painting has no portable semantic-node channel across terminal emulators and assistive software.
For sequential output, use `NO_COLOR=1`, `--color never`, and the ordinary CLI (`ready`, `tasks`,
`show ID --body`, `why ID`, `check`, `verify`, and `graph`) or a JSON format where available.

## Terminal support and recovery

The public hosted matrix passed on Linux x86_64, macOS arm64 and Windows x86_64 on 2026-11-03.
Linux and macOS ran the four portable PTY cases; Windows ran the three cases that do not require a
POSIX signal. Linux also carries the full Unix signal and job-control suite in the complete local
profile. The manual record remains narrower: it includes a partial tmux smoke pass, while an
SSH-allocated TTY and the named GUI emulator matrix remain unobserved. Automated ConPTY coverage
does not claim a Windows console-control event that its harness cannot generate.

Normal quit, `Ctrl-C`, catchable Unix termination, suspend/resume, panic unwinding and partial
initialization restore the modes the process acquired: raw mode, alternate screen, cursor,
focus/mouse reporting and bracketed paste. `SIGKILL` and `SIGSTOP` cannot be caught by any child.
If the process is forcibly killed or the host terminal itself fails to restore, run the terminal's
`reset` command; that is emergency recovery rather than the expected exit path.

Known limits are explicit:

- there is one bounded worker; a non-cancellable configured provider can delay shutdown after the
  terminal has already been restored;
- a graph window is deliberately bounded, and a static complete export is sometimes the better
  view;
- no file watcher or asynchronous runtime is added; focus gain, a five-second identity probe and
  `r` provide freshness without replacing a complete snapshot with an incoherent one; and
- the TUI does not commit Git history, run a shell, host MCP, generate batch artifacts or select a
  different repository after launch.

For implementation rationale, measured dependency and binary costs, lifecycle proofs and the full
interaction contract, see [`design/tui.md`](design/tui.md). For every exact action and CLI boundary,
see the generated [`TUI action reference`](tui-reference.md).
