# Adopting a build that has not been released

For a repository that stages the `aplan` binary itself rather than pinning a published release,
which today is any repository that needs a feature newer than `v0.5.2`. The work described on this
page shipped across `v0.3.0` and `v0.4.0`, so a repository that staged a build to get one of these
features can now pin a release tag instead.

If you pin the action (`uses: asamarts/aplan@v0.5.2`), none of this applies: you get the release
that tag names, and you adopt a new one by changing the tag.

## Upgrade the binary first, then the config

**This ordering is not a style preference. Reversing it breaks the gate outright.**

Unknown keys in `.aplan.yml` are a hard error, deliberately, so that a misspelled `requre_effort`
fails loudly instead of being ignored. The whole config fails to load rather than the one key being
skipped, and the gate then refuses to run at all -- **every command that reads config, not just the
one you ran**. You do not lose the new feature, you lose `aplan`, and if your pre-push hook runs it
you lose the ability to push. This happened to the first adopter and is tracked as `A1-068`.

The cost of that strictness is that a key from a newer `aplan` looks exactly like a typo. Both
report the same way:

```console
$ aplan check
aplan: loading .aplan.yml: /repo/.aplan.yml: unknown key `requre_effort` (did you mean `require_effort`?)
note: this is aplan 0.3.0-dev, which accepts 37 config key(s); `aplan facts` lists them. A key added by a newer aplan reads exactly like a typo from here, so if you staged this binary, upgrade it before adopting the key (`docs/upgrading.md` leads with that ordering).
```

**Read the parenthesis.** A misspelling usually gets a correction, because the key it was near is
one this build knows. A key from a newer `aplan` gets none, because there is nothing near it here.
This is the same repository and the same command, run against a binary staged a day earlier:

```console
$ ./staged/aplan check
aplan: loading .aplan.yml: /repo/.aplan.yml: unknown key `docs`
note: this is aplan 0.3.0-dev, which accepts 32 config key(s); `aplan facts` lists them. [...]
```

Two things separate that from the transcript above, and neither is the version, which both builds
report as `0.3.0-dev` -- a pre-release cannot tell two builds from `main` apart, which the next
section is about. The first is the missing suggestion. The second is the count: this binary accepts
fewer keys than the one above it, and the key it is refusing is one of the ones it has never heard
of.

Both are hints rather than proofs -- a typo far enough from any real key also gets no suggestion,
and a count tells you two builds differ without telling you how. `aplan facts` settles it, and it is
the one command that reads no config, so it still answers while everything else refuses.

So: stage the new binary, confirm `aplan check` still passes on your existing config, and only then
add the new keys.

**If you need an answer before you can upgrade**, `aplan --no-config ready` runs a read-only query
and says what it did not apply, and `aplan --config ./older.yml ready` reads a file you name instead
of discovering yours. Neither is a fix and neither belongs in a gate -- the first skips the policy your
repository declared -- but `aplan why`, `ready` and `show` will answer under them while the binary
is still the old one.

## Knowing which build you have, and what it can do

A development build from `main` reports the next pre-release version (`0.6.0-dev`) and the
published release reports its own (`0.5.2`), so the two can never be confused. That was not always
true: every build from
`main` used to claim the released version, which meant a check like
`aplan --version | grep -qF 'aplan 0.2.0'` passed for a binary that could not run the gate at all
(`A1-060`).

The version still cannot tell two builds from `main` apart, so record the commit when you stage:

```sh
git -C <aplan-checkout> rev-parse HEAD    # write this down next to the sha256
```

**Prefer asserting a capability over a version.** `aplan facts` reports `config_keys`, every key
this build accepts, derived from the schema it validates against rather than hand-listed:

```console
$ aplan facts | jq -r '.config_keys[]' | grep covers
test.covers
```

That is the question a staged binary actually has to answer, and it survives a version bump. Assert
it rather than searching for it:

```sh
aplan facts --require test.covers --require APLAN024 --require tasks
```

For a staged interactive build whose task view must agree with CLI selection and readiness, assert
`aplan facts --require build.tui --require tui.task_browser_preserves_selector_semantics --require
tui.task_browser_state_is_refresh_and_repeat_safe --require
tui.task_inspector_uses_show_projection --require
tui.inspectors_use_semantic_information_hierarchy --require
tui.work_discovery_is_one_typed_flow --require
tui.report_hub_preserves_cli_report_semantics --require
tui.onboarding_and_capabilities_are_typed`. The first name distinguishes a headless build;
the second distinguishes the foundation shell from the searchable/filterable browser; the third
pins its corrected repeat-event, refresh-cursor and hidden-selection state; the fourth requires
the complete, linked inspector and body search; the fifth requires typed inspector hierarchy and
stable narrow reflow; the sixth pins its ready/why/due workflow; and the seventh retains typed
report semantics. The final name requires classified first-use/repair screens,
in-place retry, visible root/configuration trust choices, and an About view derived from the same
typed inventory as `aplan facts`. These views need no new configuration or runtime dependency.

If the staged workflow must remain useful on short or narrow terminals, also require
`tui.shell_adapts_by_route_and_available_rows`. That build chooses pane composition from width and
chrome density from height, keeps a route/subject/back breadcrumb and palette/help discovery at the
48x14 floor, gives each route and overlay a measured compact composition, and preserves selection,
graph and uncommitted form state across resize. Below 48x14 it refuses cleanly while retaining
`Esc`, `q` and `Ctrl-C` exit paths. It adds no configuration or runtime dependency.

If report discovery or literal configured-command presentation is part of the staged workflow,
also require `tui.report_discovery_is_literal_and_parameter_safe`. That build uses `/` for report
and row search, exposes Stale work's as-of date separately with `d`, and preserves argv boundaries
when it names `version.current.command`.

If an interactive workflow depends on live repository state, require
`tui.external_refresh_is_identity_safe`. That build displays separate plan, resolved-config, HEAD
and Git-status identities; probes them every five seconds while active and on focus gain; and
rechecks after building a replacement snapshot. Manual `r` remains available. A raced, invalid or
unloadable reload keeps the previous complete snapshot and says it is unconfirmed instead of
presenting mixed state as current. No watcher service, async runtime or new runtime package is
required. Focus-change reporting is acquired and restored with the other terminal modes; a result
started before focus loss cannot silently promote an inactive snapshot back to current. To also
exclude the narrower case where focus returns before that old result is delivered, require
`tui.focus_epoch_invalidates_external_results`; that build binds probe and refresh work to a focus
epoch and immediately confirms any crossed-epoch replacement with a new probe.

If terminal job control can suspend the process, also require
`tui.suspension_invalidates_snapshot_freshness`. That build treats `SIGTSTP` as a stronger focus
loss: it advances the observation epoch and marks retained bytes unconfirmed before stopping.
`SIGCONT` repaints that honest state and requests a current-epoch observation immediately. If
deliberate work still owns the bounded worker, the request stays due and starts as soon as capacity
returns rather than waiting for the next five-second interval.

For a staged build that depends on the portable terminal lifecycle, require
`tui.terminal_portability_is_explicit`. It names a shared real-PTY module for focus, resize,
minimum-size recovery and clean/interrupt teardown, plus an evidence matrix that does not turn an
unavailable private macOS or Windows runner into a pass. Once public, the weekly/manual workflow
runs that module on standard hosted Linux, macOS and Windows; Unix signals and job control remain a
separate Unix contract.

To depend on Ctrl-E body editing from the Add form, also require
`tui.external_editor_handoff_is_safe_and_identity_bound`. The build restores terminal modes before
starting parsed `VISUAL`/`EDITOR` argv directly, bounds and removes its private draft, routes the
returned Markdown through ordinary preview and confirmation, and re-observes repository inputs on
resume. A complex editor command that needs shell syntax must be placed in a wrapper script; aplan
does not interpret pipes, redirections or substitutions.

Supervisors that can deliver stop and continue signals in rapid succession should additionally
require `tui.continue_cancels_pending_suspend_handoff`. It covers the narrow handoff after the
screen has restored terminal state but before the default stop handler runs: a continue observed
there cancels the stale stop instead of being consumed just before the process suspends and waits
for a second signal. Termination and a separately observed suspend remain dominant.

If a supervisor can use `SIGSTOP`, or repository freshness after any continue matters, require
`tui.continue_establishes_freshness_boundary`. `SIGSTOP` itself remains uncatchable, so no child can
restore modes before it stops. Its later `SIGCONT` is observable: that build treats every continue
which resumes interactive work as a focus epoch boundary, labels retained bytes unconfirmed and
requests a current-epoch observation. It also covers the cancelled handoff above and does not
double-advance an epoch already invalidated by handled `SIGTSTP`.

To require that frequent observations do not silently pay the full refresh preparation cost, add
`tui.production_external_probe_avoids_refresh_work`. That build resolves the same production input
identity, including configured documents and repository state, through a dedicated input-only
loader. Verification sheets and report projections are constructed only for a refresh, whose
post-projection confirmation uses the same observation path.

If a verification provider or other background operation may run longer than the polling interval,
also require `tui.overdue_external_probe_is_fail_closed`. That build changes the freshness label to
unconfirmed when the sole bounded worker cannot start a due probe, leaves the deadline due, and
probes immediately when capacity returns instead of waiting another interval. It does not queue
over, cancel or run concurrently with deliberate user work.

If interactive exit latency is part of the integration contract, also require
`tui.quit_starts_no_new_work`. After input requests quit, that build gives termination and
suspension precedence, treats continue as inert, and exits before draining a completion that could
start queued work, starting an external probe, drawing another frame or polling for more input.
Work that was already running still follows the graceful-shutdown and termination-preemption
contract; queued work that never started is discarded.

For the hardened layered graph rather than an earlier nominally complete scene, require both
`graph.layered_scene_is_complete_or_fallback` and
`graph.layered_hardening_corpus_is_executable`. The first refuses to paint or hit-test a current
scene unless every admitted edge, non-empty phase band and semantic identity has validated
geometry; retained geometry is recovery input only, and any failure becomes an explained,
selectable fallback. The second identifies the build whose executable corpus covers hostile graph
shapes and every four-node DAG in both orientations, with exact edge provenance, phase
containment, valid ports and routes, typed feedback, determinism and total accounting.

If the matched readability gate matters too, require
`graph.layered_routes_choose_low_bend_ports_within_crossing_budget`. The hardening names above
prove complete safe geometry; this additional name proves both orientations stay within Lanes'
unrelated-crossing count and 125 percent bend limit on the same crossing-heavy graph.

For a large plan whose plan and phase overviews must remain traversable, also require
`graph.aggregate_levels_are_bounded_and_continuable`. That build selects a source-bound semantic
window of at most 10 aggregate cards and 20 visible aggregate edges before layout, honors a
tighter client budget, and reports exact raw-task/dependency omissions plus continuations. An
older layered build can send the complete aggregate source to the 64-node cell-scene ceiling and
fall back or refuse even though a bounded overview would fit. This capability does not raise that
ceiling or change milestone/task detail limits; it makes partial admission explicit rather than
presenting a clipped source as complete.

If graceful TUI shutdown and concurrent resize/input delivery are integration requirements,
require `tui.external_observation_is_shutdown_cancellable` and
`tui.simultaneous_resize_and_input_are_not_lost`. Those names distinguish a build whose repository
observations yield to worker cancellation at identified load boundaries and whose Unix terminal
source consumes queued input before a simultaneous resize notification. Together they prevent a
restored terminal from waiting on an observation and prevent a queued quit key from being stranded
after `SIGWINCH`.

For bounded graph work on large plans, require
`tui.hidden_graph_resize_defers_reprojection`,
`tui.graph_fallback_paint_is_viewport_bounded` and
`tui.graph_selection_reuses_current_projection`. That build does not reproject a hidden Graph
destination during resize, formats only the visible fallback row slice after caching its extent,
and updates selection-independent plan or phase focus in place before reusing current cell
geometry. Task-level bounded detail still reprojects around its new anchor because selection is
part of that projection.

For refresh latency that does not scale with every hidden destination, also require
`tui.refresh_rebuilds_only_the_visible_projection`. Refresh adopts the coherent snapshot and
reconciles the visible destination plus shared work and inspector state. Hidden Tasks, Graph and
Reports projections rebuild from that adopted snapshot only when entered, so deferral cannot
display a projection from an older source identity.

The report-hub capability pins a stronger boundary than the presence of the Reports tab. Builds
carrying it retain typed CLI-equivalent values for roadmap, summary, version, paths, vacuity,
stale and deprecation views; state selector scope explicitly; distinguish unavailable inputs from
empty or measured-zero answers; and drill through exact contributor ids. It needs no new
configuration. Opening Version names but does not execute `version.current.command`; stale and
path observations read only the identified local repository.

Anything the build advertises: a config key, a rule code, a command, an output format, an
evidence kind, a named behaviour, an MCP tool, or an enabled build capability. Repeatable; naming
one twice is one question, and a blank one is a usage error. Every missing capability is named, and the
two failures stay apart: a build that answers "no" exits **1** and lists what it lacks, while a
build too old to be asked has no such flag and exits **2** with `unexpected argument '--require'`.
Conflating those is how the first adopter's hand-written check told an operator a binary lacked a
key it supports.

The `grep` this replaces still works, and is what a build older than this flag has to do:

```sh
aplan facts | grep -qF '"test.covers"' || { echo "staged aplan is too old" >&2; exit 1; }
```

## Building a stageable binary

The published artifact is statically linked, and a binary you build yourself must be too. The
obvious build is not:

```console
$ cargo build --release && podman build ...
aplan: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.38' not found (required by aplan)
```

A dynamically linked build carries the glibc of the machine that built it. A build host on glibc
2.39 produces a binary that a Debian bookworm runner image (2.36) cannot start, and you find out
at image build time or, worse, on the first CI run.

Two traps sit on the direct route, so do not take it:

- `rustup target add x86_64-unknown-linux-musl` adds the target to the *active* toolchain, and
  `rust-toolchain.toml` selects a different one once you `cd` into the repository. The resulting
  `can't find crate for 'core'` error suggests running exactly the command you just ran.
- Even with the target present, the build needs a musl C toolchain, because `aplan` links libgit2
  and zlib: `error occurred in cc-rs: failed to find tool "x86_64-linux-musl-gcc"`.

Build in a container whose native target is already musl, which sidesteps both:

```sh
podman run --rm -v "$PWD":/src:Z -v "$PWD/out":/out:Z -w /src \
  docker.io/library/rust:alpine \
  sh -c 'apk add --no-cache musl-dev && cargo build --release -p aplan --target-dir /out'
```

No `--target` flag is needed: on Alpine the host target *is* musl. Verify before staging, rather
than discovering it in CI:

```console
$ file out/release/aplan
out/release/aplan: ELF 64-bit LSB pie executable, x86-64, static-pie linked, stripped
$ ldd out/release/aplan
	statically linked
```

Measured at about 2m20s from a cold container on a warm source tree.

Needing any of this is a symptom of `A1-060`: if a release carried the features you need, you
would download it.

## Which of these are for you

An adopter reads a "what is new" list as a list of things to do. Some plans use descriptive tags
rather than a second grouping level, and some use cuts as parallel slices rather than a pipeline.
Those plans should be able to identify and skip features that do not fit their model.

So this table is the other half of the list below. It is written in the *plan's* terms, never in
benefits, and the right-hand column is the one to read first: it is what lets you skip a row.

Everything here is off until you ask for it, with one exception, which says so in its own row:
`require_effort` is on, and the decision is whether to turn it off.

There is deliberately no command that answers this for you. It was measured before it was rejected
(ADR-0024): a plan's shape predicts which grouping features fit it, and does not predict the rest.
The same signals can describe sequential cuts or parallel slices. That distinction is intent, and
this tool does not read intent.

| Feature | For you if your plan | Not for you if |
|---|---|---|
| `capture` | needs a shared, versioned intake queue for ideas or notes that are not actionable tasks yet, and more than one adapter or checkout must see the same records | already records only actionable work, or keeps intake in an external system. An empty or absent `.inbox` is valid, so do not add capture configuration merely because the key exists |
| `policy` | holds work judged to different standards -- a release cut that must close on a test where a spike may close on a note -- and you are currently saying it with `evidence.exempt_tags`, which can only switch the requirement off entirely | has one standard for everything, which is most plans. A scope is a second place policy can live, and two places to look is a real cost: prefer raising or lowering the whole-plan value while it still fits |
| `tag_families` | has tags that cluster into a vocabulary -- `epic-auth`, `epic-sync`, `kind-spike` -- and you want a typo in one refused | your tags are flat descriptive words (`ci`, `spec`, `docs`), where a typo costs nothing that `APLAN022` does not already catch |
| `owners` | assigns tasks from a stable team roster and wants misspellings or departed aliases reported | leaves tasks unassigned, imports owner names from another system without a controlled roster, or intentionally treats any string as a valid owner |
| `roadmap.group_by` | declares `tag_families` and has cuts big enough that a flat member list is hard to read | declares no family, or your cuts hold a handful of tasks each |
| `summary.group_by` | declares `tag_families` and repeatedly needs effort, completion and readiness by one family instead of by phase | needs an occasional rollup, where `aplan tasks --format json` and `jq` avoid making the view repository policy |
| cut sequencing (a milestone in a milestone's `blocked_by`, ADR-0013) | has cuts that are *stages*: the next one starts when the last one closes | has cuts that are parallel slices of one release. Milestone edges between them make `ready` shorter by misrepresenting what waits on what |
| a `release` milestone (the `release` tag, ADR-0022) | ships several cuts together and is judged on the release rather than on the cut | has one cut per release, where the cut already is the delivery point |
| `prefer_after` (ADR-0025) | has work the graph leaves free to order, and an order you want anyway | has an order that dependencies already force, or no opinion about what comes first |
| `effort_days_per_week` (ADR-0023) | carries `effort_days` and you have *measured* how much of it a week absorbs | has not measured it. A borrowed multiplier makes every derived duration wrong at once |
| `test` runners with `covers` | has more than one test-listing scope (a workspace of crates, an umbrella of components) | runs one test command that lists everything, where a citation cannot be ambiguous |
| `url.check` | cites `url` evidence you want resolved rather than trusted | cites no urls, or cites ones that need credentials your CI does not have |
| `evidence.require_min_strength` | wants `done` to mean a machine could check it. **Which value is a stage, not a taste**: start at `[commit, test, file]` with one exempt tag you review, and narrow to `[test]` once a runner exists to point at. `aplan`'s own `[test]` is the far end of that arc, not the starting line | is still being written, where refusing weak evidence refuses the plan you are drafting |
| `advisory` | has a rule that is right in general and wrong for this repository, and you would rather report it than turn it off | can fix what the rule reports, or `deny_warnings` is already off |
| `deny_warnings` | wants every warning to block, because a warning nobody blocks on is a warning nobody reads | is adopting incrementally and needs the warnings visible before they are fatal |
| `require_cut_membership` | wants a cut's `done` to prove the slice is exhaustively complete | keeps work outside cuts on purpose, where every task would need `cross-cutting` to say so |
| `require_effort: false` (it defaults to **on**) | does not estimate, where leaving it on makes `APLAN009` name every task without `effort_days` | estimates, or intends to. This is the one row here that turns something *off* |
| `version.require_impact` | ships an artifact whose number is supposed to follow from the work -- a library, a CLI, anything with consumers reading a changelog -- and you want the plan to be the place that says what a release owes | ships nothing versioned, or versions on a calendar, where a task's impact on the number is not a thing anyone has to know. The level floors (`version.levels`) are the second decision, and only if the defaults read wrongly: a plan whose cuts are planning buckets rather than deliveries sets `cut: none` |
| `detect_drift` | traces sections of documents that must not change quietly under a closed task | traces nothing, or traces documents that churn for reasons unrelated to the task |
| `traces_external` (`APLAN034`) | traces a document that lives outside this repository | traces only files it checks out, which is every plan that has not seen this error |
| `traces_root` | resolves `traces` paths from somewhere other than the directory you run `aplan` in | traces paths that already resolve from there |
| `no_traces` | has no traced documents and wants the checking off entirely | traces anything at all |
| `test.output_lines` (`A1-365`) | has tests that print things you would rather not publish, in which case `0` suppresses the output entirely; or tests whose failures need more than eight lines to explain, in which case raise it | is content with the default. The output is already bounded, redacted and sanitized, and the common failure explains itself in a handful of lines |
| `max_output` on a test runner, url checker or declared version command (`A1-366`) | has a configured command whose useful catalogue, value or failure tail can exceed 1 MiB on either stdout or stderr | is content with the default. This bounds bytes retained in aplan's parent process, not the child and not the finding; raising it spends that memory per stream |
| `test.batch` (`A1-642`, ADR-0054) | runs `verify --execute` over enough distinct cited tests that framework startup and collection dominate. It requires a repository-owned adapter that can map exact listed identities to a native structured report and publish every terminal outcome | has few cited tests, cannot attribute its framework's results exactly, or prefers the zero-adapter legacy path. `test.run` remains required and has no deprecation date |
| Focused L3 close (`A1-705`, `A1-708`, ADR-0061, `--require close.focused_l3_is_explicit_scoped_and_stale_safe`, `--require close.focused_l3_terminal_outcomes_name_external_effects`) | has tasks whose cited test should pass before the `done` write, but whole-plan `verify --execute` is too broad for the authoring loop. Use `aplan close ID --evidence test:NAME --execute` only after reviewing trusted runner configuration; it runs repository code | needs only L2 identity resolution, is reviewing an untrusted pull request, or closes through MCP. Ordinary close and `aplan_close` remain L2-only. A focused run executes only the proposed closure's distinct test identities and aplan publishes no plan mutation on a non-pass or stale input. Every terminal outcome after configured code starts distinguishes aplan's guarded publication from the command's own effects, which are not rolled back; inspect the working tree after it runs |
| `test.schedule` with `test.runners` (`A1-643`, ADR-0055) | has independent runners whose catalogue or batch work dominates the gate, and can declare a measured aggregate `capacity`, conservative per-runner `weight`, and any capacity-one `exclusive` resources they share | has one runner, does not know its safe resource budget, needs a machine-wide/distributed lock, or is content with serial execution. Existing single-runner and sequence forms remain serial; concurrency is never inferred |
| A per-user `me` (`A1-364`) | works more than one repository from one machine, or runs the MCP server from a desktop client that sources no shell profile -- there is no `APLAN_OWNER` to inherit there, and the next guess is `git config user.name`, which on the machine this was measured on said `t` | already exports `APLAN_OWNER`, or passes `--as` from a script, where a file is a third place to look for a value you have already said |
| Local ephemeral claims, `--unclaimed`, and holder/time/origin in read surfaces (`A1-531`, ADR-0051) | is worked by more than one person or agent at a time, especially through linked worktrees, where "who is on this now" must be visible before a commit exists without replacing the role or team responsible for it | has one actor, where every claim says the same thing. Durable `owner` is still useful independently. Claims coordinate only worktrees sharing one local Git common-directory filesystem; they are not a cross-host lock, authenticated identity or distributed scheduler |
| `id_strategy: ulid` (`A1-047`) | has authors minting ids in **separate checkouts** and colliding at the merge: neither writer can see the file the other wrote, so nothing detects the collision until both are pushed and no retry can help | has one author, or many writers against **one** checkout, a fleet of agents included. Concurrent `add` re-mints when it loses an id (`A1-230`), measured at 24 of 24 landing, so sequential is the right answer there and you keep readable ids. A ULID is not memorable, in every `blocked_by`, every `why` and every filename |
| `root` | keeps task files somewhere other than `aplan/` (the default), as `plans/tasks` or similar | keeps them there |
| `--config` / `--no-config` (`A1-155`) | runs `aplan` over checkouts it does not control -- a review bot, a CI job judging a fork PR, a pinned binary auditing a candidate release | only ever runs it inside its own repository, where discovering that repository's `.aplan.yml` is exactly what you want |
| `aplan paths` (`A1-151`) | wants to know whether its `commit` evidence is doing work -- typically when adopting, or when a cut's tasks all declare the same tree | has narrow `paths` already, or is a single-component project where one directory genuinely is the work and a broad share is the honest answer |
| `stale_after_days` / `aplan stale` (`A1-020`) | has work that can sit unnoticed -- a backlog bigger than one person holds in their head | closes what it starts, or reviews the plan often enough that a report of what has sat tells it nothing it did not know |
| `aplan stale --as-of` (`A1-162`) | reviews a plan on a cadence, and wants "how does this look today" rather than "how did it look at the last commit" | runs `stale` in CI on every commit, where `HEAD`'s own time is the answer you want and the default already gives it |
| Evidence citations in generated guidance are shell-safe (`A1-156`) | **regenerate `AGENTS.md`**, and expect the import notices to read differently: an angle-bracket placeholder after `commit:` was redirection in an unquoted shell word, so the close example failed at parse time rather than running | `commit:COMMIT_SHA`, `test:REGISTERED_TEST_NAME`, `file:FILE_PATH`, `url:URL` -- inert, conspicuous, and copy-safe. Prose naming a form (`aplan tree <id>`) keeps its angle brackets, because there the reader is choosing the subject rather than copying a line |
| Generated guidance scopes three rules to non-milestone tasks (`A1-157`) | **regenerate `AGENTS.md`**: three bullets said "every task" about rules that exempt a milestone, so a valid cut container read as noncompliant and an agent following the block literally would add a meaningless estimate and `paths` to it | the bullets for `paths` (`APLAN023`), `effort_days` (`APLAN009`) and cut membership (`APLAN022`) now say "that is not a milestone". **Nothing about milestone validation changed** -- a milestone still needs neither field, and never did |
| `aplan vacuity` (`A1-114`) | is adopting, and wants to know how much of the evidence gate is actually running rather than passing vacuously | has `paths` on every task already, where the answer is "all of it" and the report says so in one line |
| `aplan export-roadmap-json` (`A1-033`) | keeps a status file another build reads, and is tired of it drifting from the plan | has no such file, or generates it from something else already |
| A section-naming `file` citation (`A1-159`) | proves work with written records -- an incident report, a reviewed audit, a decision log -- where the proof is a section rather than a whole document | proves work with commits and tests, where a document citation would be the weaker claim anyway |

## Resolving a sequential-id add/add conflict

This section is for a repository that chose readable sequential ids and sometimes mints them in
separate checkouts. Writers sharing one checkout are already safe: `add` retries an id another
writer took (`A1-230`). Separate branches cannot see each other, so both can legitimately create
the same next id. Git reports that as an add/add conflict when the branches meet.

**Treat each side of every conflicted task file as a separate task until reading it proves
otherwise.** It is not two edits to one logical file merely because its path is the same. Choosing
ours or theirs wholesale can silently delete a task. While the merge is unresolved, inventory both
stages by content:

```console
$ git diff --name-only --diff-filter=U -- aplan/
$ git show :2:aplan/tasks/A1-047.md
$ git show :3:aplan/tasks/A1-047.md
```

Replace `aplan/` with the plan's configured root when it differs.

The words "ours" and "theirs" change meaning during a rebase, so decide by title and body, not by
stage number. Make an explicit table with the old id, both titles, and the disposition of each.
Allocate every replacement id against the combined namespace before editing any reference. Usually
the unlanded side moves; genuinely duplicate work may instead be consolidated, but only after the
table records which body and acceptance criteria absorbed it.

For every task that moves, update its frontmatter `id`. If its filename encodes that id, as an
`add` scaffold's does, rename the file too; aplan's identity is the field rather than the path, so
a differently named file stays differently named. Then update all structured references in every
task: `blocked_by` (including a milestone's membership list), `prefer_after`, `ratified_by`, and
`contains`. When a milestone moves, inspect `.aplan.yml` too: a `policy[].when.cut` value may be
that milestone's id or its label, and only the id form moves. Update hand-written membership
documents such as `ROADMAP.md` too. Then find every remaining textual occurrence:

```console
$ git grep -n -F 'A1-047'
```

Read each result before changing it. A historical record, changelog, or task body may be citing the
task from the other branch that kept the old id. A repository-wide substitution is therefore unsafe:
prose citations must be adjudicated individually. Regenerate derived files only after the
hand-written map is correct, then run the same gates CI runs:

```console
$ cargo xtask gen-roadmap
$ cargo xtask check-docs
$ aplan check
$ aplan verify
```

Git's add/add conflict is the mechanical check. A custom merge driver would run one file at a time,
without the merged id namespace or the ability to update references atomically, and could hide the
only reliable signal. A post-merge check cannot recover a task already discarded during conflict
resolution. The bounded operation delivered by `A1-409` begins only once both task files have been
preserved: run `aplan rekey OLD NEW`. It updates the
frontmatter id, every structured task reference, a conventional filename, and any milestone policy
that names the old id as one guarded change. A custom filename stays custom. The command reports
remaining exact-token occurrences by path and line but never rewrites them: adjudicate each one
using the table above, then regenerate the derived files. Git history, published links, external
documents and other repositories remain unchanged; terminal tasks require `--allow-terminal` to
acknowledge that durable boundary. If separate-checkout collisions are routine rather than
exceptional, use `id_strategy: ulid` and avoid this repair class entirely.

## Exporting portable test-evidence receipts

A receipt is a correctness-bearing artifact, not a build cache entry. Publish one only from the
job that actually owns the complete provider execution, retain it for the workflow or release
window that can still authenticate its producer, and restrict artifact readers accordingly.
Deletion is safe and costs a rerun; accepting a receipt from the wrong producer can create false
proof. Diagnostics use a hard bound and best-effort credential redaction, not a secret scanner. Set
`test.output_lines: 0` when a test can print secrets in shapes no redactor can recognize.

Receipt production requires explicit producer coordinates because JSON cannot authenticate itself.
The following GitHub Actions shape belongs in a trusted `push` job, not an untrusted fork job:

```yaml
- name: Export backend test evidence
  if: github.event_name == 'push'
  run: >-
    aplan test receipt backend --output backend.test-evidence.json --producer-repository "$GITHUB_REPOSITORY" --producer-workflow "$GITHUB_WORKFLOW:$GITHUB_JOB" --producer-run-id "$GITHUB_RUN_ID:$GITHUB_RUN_ATTEMPT" --producer-event "$GITHUB_EVENT_NAME" --producer-privilege trusted
- uses: actions/upload-artifact@v4
  with:
    name: backend-test-evidence
    path: backend.test-evidence.json
    retention-days: 7
```

Downloading that artifact and checking its SHA-256 establishes content integrity only. A later
consumer must also obtain repository, workflow, run, event and privilege from the authenticated
Actions context and compare them with the statement. If the workflow adds GitHub artifact
attestation, the DSSE policy additionally binds the externally verified payload and producer; aplan
does not treat the envelope's own signature text as verification.

The equivalent GitLab job uses ordinary job artifacts and runs only in a protected context:

```yaml
backend-test-evidence:
  rules:
    - if: '$CI_COMMIT_REF_PROTECTED == "true"'
  script:
    - >-
      aplan test receipt backend --output backend.test-evidence.json --producer-repository "$CI_PROJECT_PATH" --producer-workflow "$CI_CONFIG_PATH:$CI_JOB_NAME" --producer-run-id "$CI_PIPELINE_ID:$CI_JOB_ID" --producer-event "$CI_PIPELINE_SOURCE" --producer-privilege trusted
  artifacts:
    paths: [backend.test-evidence.json]
    expire_in: 7 days
```

Mark receipts from merge-request or pull-request code `untrusted`; do not promote them by changing
the field after download. Same-workflow trust requires the independently recorded artifact digest
and producer coordinates to match. Signed trust requires an externally authenticated DSSE payload.
Local-file trust is for a caller-controlled filesystem boundary, not for an arbitrary downloaded
file.

Timestamps and the recorded Git revision are audit context. They do not expire a result or make it
current. Currency comes from exact runner, catalogue, material, environment, toolchain and aplan
identity. A configured policy may allow source revision movement only while all of those stronger
identities still match.

To consume receipts, trusted orchestration creates an `aplan/test-evidence-import-set/v1` document
with exactly one entry per configured provider, then runs:

```sh
aplan verify --test-receipts test-evidence.import.json
```

The committed schema is `schemas/v1/test-evidence-import-set.json`. Receipt paths are relative to
the import set unless absolute. `local_file` is appropriate only when the consumer controls the
filesystem boundary. For `same_workflow`, populate the artifact digest and producer coordinates
from authenticated workflow metadata; for `signed`, populate the payload digest and producer from
the externally verified DSSE identity. Never let pull-request or other untrusted repository code
author the manifest that declares those facts: the manifest is caller-owned policy input, not its
own authentication.

The command recomputes current identities and derives a new verdict over the exact current plan.
It does not run `test.list`, skip queries, probes, batches or exact tests, and it does not silently
fall back. An absent, stale, partial, untrusted, incompatible or faulty provider is a typed finding.
Use `verify --execute` deliberately for full direct replay. `--test-receipts` therefore conflicts
with `--execute` and `--fix`. For a locally controlled import set, incremental refresh is explicit:

```sh
aplan verify --refresh-test-receipts test-evidence.import.json --refresh-base origin/main --refresh-head HEAD
```

Use `--refresh-working-tree` instead of `--refresh-head` to include HEAD, index, tracked edits and
untracked files. Without `test.inputs_by_test`, every invalidated provider runs completely. With the
key, every current test and relevant changed input must have exactly one owner or the provider
widens. This declaration says what can change a result; `covers_by_test` continues to say what a
result proves. Refresh publishes only a complete manifest and cannot locally replace a
`same_workflow` or `signed` row.

## What a `test` runner costs, and what it can see

Read this before you decide where your plan gate runs. Every claim below was run rather than
reasoned about; the commands are the ones you would type.

**Plain `verify` runs your `test.list`, and for a cargo runner that compiles.** `--execute` is the
flag documented as running your tests, and it is easy to read that as "without it, nothing is run".
Not so: resolving a `test` citation means asking each runner what it lists, so `verify` invokes
`test.list` whether or not you pass `--execute`. On a one-file crate with no `target/`, a plain
`aplan verify` left a 7.3M `target/` behind it. The sharper proof is what happens when the tests do
not compile:

```console
$ aplan verify
error[APLAN013]: the `cargo` test runner could not be asked what it lists, so no `test` citation
it would have resolved could be checked: running `test.list` for cargo: `cargo test -q -- --list`
exited 101 (error[E0308]: mismatched types)
```

No `--execute`, and a compiler error. That is the listing building your test binaries.

**So the gate needs whatever your build needs.** If your test workspace path-depends on a sibling
checkout, a plan gate that clones only your repository fails on every run, and the message is about
the runner rather than about anything in the plan:

```console
$ aplan verify        # with the sibling moved aside
error[APLAN013]: the `cargo` test runner could not be asked what it lists ...
(error: failed to get `sibling` as a dependency of package `mainrepo`)
```

Fold the plan gate into a job that already has the tree, rather than giving it a job of its own.

**Budget for it.** This repository's own plan, warm, across ten cargo runners: `aplan verify` takes
about 31 seconds, and that is with everything built. The first run on a cold tree is a full build of
every runner's targets, which can take minutes and is what `test.timeout_seconds`
(default 600) is sized for. If your gate is slow the first time and fast afterwards, this is why,
and `aplan check` is the fast half that never opens any of it.

**A runner sees one feature set.** A test behind a feature flag is not in a default runner's
listing, so the citations proving that work are exactly the ones it cannot resolve -- and the
finding blames the citation, not the runner:

```console
$ aplan verify
error[APLAN013] T-1: test `tests::telemetry_is_emitted` is not one the configured runner lists
```

Adding the feature to the runner's `list` argv resolves it. Configure one runner per feature set you
cite tests from, and `expect_tests: false` for a component that has none yet.

**Cite the name `test.list` prints, not the path you would write in Rust.** For an integration test
in `tests/session.rs`, `cargo test -- --list` prints the bare function name, so the file-qualified
form fails. You do not have to guess, because the diagnostic does the correcting:

```console
$ aplan verify
error[APLAN013] T-1: test `tests/session.rs::assembled_prompt_reaches_the_request` is not one the
configured runner lists, but `assembled_prompt_reaches_the_request` is
  fix: Cite `assembled_prompt_reaches_the_request`, which is how the runner reports it. Run
       `aplan test list` to inspect the exact configured names.
```

Run `aplan test list assembled_prompt` and cite the returned non-ambiguous `test:` value unchanged.

### Batching cited test execution

Add `test.batch` only after upgrading the binary; an older build refuses the unknown key. The
legacy `run` key remains mandatory and is used whenever `batch` is absent:

```yaml
test:
  list: ["pytest", "--collect-only", "-q"]
  run: ["pytest", "-q", "{test}"]
  batch:
    protocol: 1
    run: ["python3", "ci/aplan_pytest_batch.py", "{manifest}", "{result}"]
```

The adapter reads `aplan/test-batch-manifest/v1`, passes every exact pytest node id to one native
run, and converts its structured or JUnit result to `aplan/test-batch-result/v1`. Vitest adapters
must preserve both file and full test-name identity rather than feeding `vitest list` output
blindly to `--testNamePattern`; Playwright adapters likewise bind file/title selections to its blob
or JSON result before merging shards. In all three cases, a successful native command with no row
for a requested identity is `unavailable`, never `passed`.

The result repeats the manifest nonce and provider, says `complete: true`, and contains exactly one
row per request with `passed`, `failed`, `skipped`, `stopped` or `unavailable`. Write it beside the
supplied destination and rename it into place only after all rows are final. Aplan refuses a
missing, duplicate, extra, malformed, replayed, symlinked or replaced result, additionally refuses
hard links and owner changes on Unix, and refuses every claimed pass when the adapter exits nonzero.
Documents are capped at 32 MiB, requests at 100,000 identities, identities at 16 KiB and raw per-row
diagnostics at 64 KiB; displayed detail then uses `test.output_lines`, sanitization and secret
redaction.

The adapter inherits the runner's `dir`, `wrap`, `max_memory`, `max_processes` and `max_output`.
Like legacy `test.run`, it is not bounded by `test.timeout_seconds`; use the framework's timeout or
one inside the adapter. Cancellation and cap breaches stop the adapter process group and leave no
clean partial answer. The adapter is trusted top-level policy and may execute tools, while task
files still name only identities returned by `test.list`.

## What you can stop doing

A guide that only says what a change *adds* leaves you carrying the workaround you built before it
existed. Twice now an adopter kept one after the tool had made it unnecessary, and in both cases
the workaround was costing something they had not priced.

**If Windows CI serializes every aplan mutation, retries the whole operation after a sharing
violation, pre-validates inbox entry types, rewrites trace commands or repository-relative paths,
normalizes a selected configuration path before `rekey`, or spells a bare configured provider as
`git.exe` solely so material identity can find it, stop** (`A2-013`). Require the behavior for the
workaround you remove: `storage.atomic_replacement_is_portable` for mutation serialization and
broad retries; `capture.regular_file_boundary_is_portable` for inbox pre-validation;
`traces.diff_command_path_is_portable` for trace commands;
`repository.path_identity_is_portable` for historical release and trace lookup;
`mcp.context_paths_are_portable` for MCP provenance path normalization;
`authoring.rekey_repository_boundary_is_portable` for selected configuration paths; and
`evidence.provider_executable_resolution_is_portable` for native bare provider spelling. Keep an
explicit path when it is part of the provider trust boundary; the widening only follows the
executable spelling Windows process launch already accepts.

**If you create a task and then separately discard or hand-edit its capture, stop** (`A1-516`).
Use `aplan inbox promote I-...` instead. It runs ordinary task validation, reports both stable ids,
and publishes the task, optional cut membership and retained promotion link as one guarded
transaction. An equivalent retry is safe after a lost response; a different retry is refused rather
than creating a second task. Require `capture.promotion_is_atomic` before removing the workaround.

**If you keep quick ideas in an unvalidated task stub, a sidecar TODO file, or an issue solely
because authoring a complete task interrupts the work, stop** (`A1-515`). Use `aplan capture
"TITLE"` for one guarded open intake record and `aplan inbox` to review actionable records without
putting them in the task graph. Bodies may come from a literal, a file, standard input or a directly
launched editor; `inbox show`, `amend`, `discard` and `restore` preserve stable identity and an
explicit lifecycle. Require `capture.inbox_lifecycle_commands` before removing an adopter wrapper,
`capture.body_is_non_vacuous` if the wrapper depends on blank and invisible body refusal, and
`capture.writer_staging_is_not_a_record` if repository automation may inspect `.inbox` while a
write is being published. Capture remains intake, not proof; promotion creates a separately
validated task and retains the capture as its immutable origin snapshot.

**If you directly edit task frontmatter to author parked work, creation-time relationships,
terminal ledger corrections, successor scope, or portfolio deferral, stop** (`A1-343`). Use the
new `add` flags or the corresponding `add --from` fields for live creation. Reconstruct delivered
history with a manifest `status: done` entry and explicit evidence; the complete batch resolves it
before writing and can add proved history to a settled cut. Use `supersede --path`/`--trace`, their
explicit clear flags, and `--body` to control the successor at creation. Use `park` with a reason,
optional revisit instant and tags, and `unpark` to reverse the scheduling state without erasing its
history. These operations are guarded and all-or-none; keep `drop` for the distinct decision that
existing work will not be done.

**If you hand-edit an old cut before creating a new cut around one of its members, stop**
(`A1-704`). Run `aplan add "New cut" --id M-new --phase 2 --tag milestone --member TASK` and
repeat `--member` for the complete move. Add `--blocked-by M-previous` when the new cut is
deliberately sequenced after another milestone. The destination creation and every source removal
are one validated guarded publication, so denied warnings never see the empty or double-owned
intermediate plan the manual workaround exposed. Assert the capability before deleting an adopter
wrapper with `aplan facts --require add.creates_cut_around_existing_members`. An MCP client can
inspect the conditional schema for the required id, phase and milestone tag. If it also uses the
new explicit `id` and `phase` fields for an ordinary `aplan_add`, require
`mcp.add_accepts_explicit_identity`; that is a separate widening from member mode.

**If your downstream packaging policy carries a `RUSTSEC-2024-0449` exception solely for aplan,
stop after upgrading to this build** (`A1-702`). aplan no longer resolves `serde_yaml_ng` or the
archived `unsafe-libyaml` package. Keep auditing the replacement graph: the maintained
`yaml_serde`/`libyaml-rs` bridge still contains translated unsafe code, and `A1-703` owns replacing
that bridge with the qualified safe-Rust parser rather than treating maintenance as memory safety.

**If you open `.aplan.yml`, change into each runner directory and replay `test.list` to discover
an evidence name, stop** (`A1-478`). Run `aplan test list [query]`; it uses the exact trusted
configuration, repository-relative runner directory, limits and normalization that `close` and
`verify` use, identifies the owning runner and marks a shared name ambiguous. Keep inspecting the
configuration when deciding whether its commands are trusted; this removes only the error-prone
manual execution used to discover their output.

**If `verify --execute` starts one framework process for every distinct cited test, stop when that
startup dominates the gate** (`A1-642`). Add one reviewed `test.batch` adapter per affected runner;
aplan then starts it once with the complete exact request and fans its typed outcomes back to every
citation. Keep legacy `run` configured as the fallback, and do not batch a framework whose native
report cannot attribute every requested identity without guessing.

**If you pass `show --no-resolve` merely to avoid a slow or hanging configured provider, stop**
(`A1-590`). Plain `show` no longer starts configured work: it promptly reports a current retained
observation or a typed non-current state. Keep `--no-resolve` only when you intentionally want to
skip even retained observations and local repository resolution. Use `--refresh-evidence` when you
intend to wait for providers, `--require-current-evidence` when a script needs freshness, and
whole-plan `verify` for the authoritative gate.

**If you clear or overwrite task `owner` to make work look claimable, stop** (`A1-531`). Owner is
now durable responsibility and `--unclaimed` reads the separate Git-common ephemeral claim store.
Keep role/team ownership in the task, claim active work explicitly, and release it when the actor is
done. If a pre-A1-531 build wrote temporary holder names into `owner`, review those values rather
than deleting all of them: the new build deliberately cannot guess which were real assignments.

**If you leave the TUI to run `ready`, `why --all` and `due --as-of` while choosing work, stop**
(`A1-429`). Open the task's Work section instead. It carries the exact ready-rank inputs and
preferences, switches the bounded explanation to the complete closure with `w`, and uses `d` for
the reproducible due clock. Follow a loaded blocker or dependent with Enter and return with Esc.
Keep using the CLI for scripts and serialized output; the workaround this removes is manual
cross-checking during an interactive session.

**If you remove a live task's old `trace_fingerprints:` block before closing it, stop**
(`A1-358`). A task reopened for a clean-history repair can still carry the stamps from its earlier
closure. `close` now replaces that accepted mapping in place with the stamps it resolves for the
new closure, or removes it when drift detection produces none. A genuinely duplicated key remains
invalid and is still rejected before mutation. Assert the replacement behavior before relying on
it with `aplan facts --require close.replaces_live_trace_fingerprints`. If the mapping may contain
blank lines or comments between entries, also require
`mutation.block_replacements_cross_yaml_trivia` (`A1-408`); builds without that fact safely refuse
the valid input when an old entry follows the trivia. The same fact covers `restamp`, evidence
repairs, and dependency/tag edits because they use the same surgical block replacement.

**If a manifest generator gives milestones `effort: 0` to satisfy `require_effort`, stop**
(`A1-369`). Milestones are exempt from the requirement because they are checkpoints rather than
work. Omit both `effort` and `paths` from an entry tagged `milestone`; a current `aplan add --from`
refuses either field before writing anything, so the generator mistake cannot leave a plan that
fails its next `check`.

**If a review job copies its trusted config inside every candidate checkout, stop** (`A1-237`).
That placement only existed to keep `APLAN034` from mistaking the external policy directory for
the reviewed repository. Keep the policy outside the untrusted tree and select it directly with
`--config <file>`; its relative values still resolve from its own directory, while the plan's
location independently supplies the repository boundary.

**If you generate cross-cut edges to sequence your cuts, stop** (`A1-073`). Before that change, a
plan whose cuts run in order had to put the predecessor milestone into the `blocked_by` of every
task in every later cut, or `ready` offered work from three cuts ahead and `critical-path` reported
a fragment. One adopter generated 81 such edges and called them "verbose, and not optional". They
are now seven:

```yaml
# M-s1.md
blocked_by: [RD1-01, RD1-02, M-s0]   # the members, and the cut this one follows
```

A milestone listing another milestone sequences the two cuts, and the members inherit it. Deleting
the generated edges changes nothing about what `ready` and `critical-path` report, which is the
point: they were derivable from the cut each task was already in.

**If you re-order work by editing `blocked_by` in a text editor, stop** (`A1-124`). `aplan dep add
<id> --after <blocker>` and `aplan dep rm` maintain the field, and refuse the edit rather than
leaving you a plan `check` rejects afterwards. The hand edit is not merely slower: it is checked
after the fact, if at all, and the four ways it goes wrong are precisely the four the command
refuses by name.

**If you pin a staged binary by its version string, stop** (`A1-060`, `A1-082`). Every build from
`main` used to report the released version, so `aplan --version | grep -qF 'aplan 0.2.0'` passed
for a binary that could not run your gate. `main` now carries a pre-release version, which fixes
that check without your touching it, and `aplan facts --require <capability>` answers the question
the version could never answer: not which build this is, but whether it can run your gate.

**If you added a proving file to a task's `paths` to quiet `APLAN025`, stop** (`A1-069`). Declare
`covers_by_test` on the runner instead. The accommodation costs more than it looks: those `paths`
also tell `APLAN012` that a commit touching only that file is relevant to the task, and tell
`APLAN024` that those paths are related, so one silenced warning quietly weakens two other rules.
The first adopter reverted it for exactly this reason, and found a genuine lost path in the process.

### `APLAN024` is the one that will surprise you

It counts the paths a cited commit touches *outside* the task's `paths`. A commit large enough to
overlap any `paths` list satisfied `APLAN012` by accident, and this catches that. It is silent
when the task also cites a test.

**If you set `deny_warnings: true`, these warnings fail your build.** Measured on the first
adopter's plan on 2026-08-06: 11 of 60 tasks, which was the same count that repository's own
manual audit had reached. Your options, in the order the diagnostic itself suggests them:

1. cite the commit that actually did the work, or add `test` evidence, which is the remedy the
   rule is steering toward
2. raise `evidence.max_unrelated_files` if your history genuinely arrived in large commits
3. set it to `0` to turn the rule off

Deciding that is work, so run `aplan verify` with the new binary *before* you wire it into a
blocking gate, and see the number first.

### `test.covers`, if you have more than one runner

`APLAN025` warns when a task cites a test from a component the task does not own. It reads what a
runner *covers*, which is not where it *runs*: a runner selecting a component with
`--manifest-path`, an npm filter, or `--rootdir` still runs at the repository root.

```yaml
test:
  - name: server
    covers: [server/**]
    list: [cargo, test, --manifest-path, server/Cargo.toml, --, --list]
    run: [cargo, test, --manifest-path, server/Cargo.toml, --, --exact, '{test}']
```

A runner declaring neither `covers` nor `dir` makes no locality claim and is silent, so a
single-runner config is unaffected. An empty `covers` is a config error rather than a no-op.

The rule judges a task's test citations together: one test covering the code the task owns is
proof, and a cross-component integration test alongside it is context, not a finding.

### `APLAN024` and `APLAN025` arrive together, and can pull against each other

Worth knowing before you adopt both, because the sequence is what makes it confusing. `APLAN024`
tells you a commit citation proves little and to cite a test. If the test you then write is a
**repository-wide invariant**, it lives wherever your harness can read the tree, often a tools
crate, and asserts a fact about a directory it is not part of. `APLAN025` reads that as proof
borrowed from another component, and you have done a day's work at one rule's instruction only to
be refused by the next.

Name the exception in the runner rather than widening its claim:

```yaml
- name: xtask
  covers: [xtask/**]
  covers_by_test:
    - tests: [invariants::*]     # `*` matches any run of characters
      paths: ['**']
```

The tempting workaround, adding the test's own file to each task's `paths`, does silence it, and it
costs more than it looks: those `paths` then tell `APLAN012` that a commit touching only that file
is relevant to every one of those tasks, and tell `APLAN024` the same paths are related. One
accommodation, two rules quietly weakened.
