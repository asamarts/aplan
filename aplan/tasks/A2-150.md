## Why

Splitting a broad task currently means editing its file, creating children, wiring edges and
deciding by convention what happens to the original effort, body, paths, traces and evidence. An
adopting repository did exactly that by hand for an oversized task, as several separate mutations
around a hand edit. A valid interruption can therefore leave a semantically partial decomposition.
The product already has guarded multi-file writes; this workflow should use them and the relation
chosen by A2-148.

## Acceptance criteria

- [x] a typed dry-run request previews every child, parent change, effort allocation, cut membership
      and dependency/decomposition edge without reserving ids or modifying files
- [x] apply uses one guarded snapshot and one atomic publication; any parse, validation, evidence,
      policy, id-allocation, concurrent-change or write failure leaves every file unchanged
- [x] the contract states how body, owner, tags, paths, traces, checked criteria, evidence and effort
      are retained, divided or refused; it never manufactures proof or silently rewrites a closed
      task's historical claim
- [x] children inherit the cut and required tag families under explicit override rules, effort
      reconciles exactly to the chosen parent/child model, and the final graph is immediately valid
- [x] empty, duplicate, cyclic, cross-cut, terminal, already-decomposed and ambiguous splits fail
      closed with actionable diagnostics; stale previews cannot apply to a newer plan
- [x] CLI, MCP and TUI use the same request/preview/apply model and deterministic machine result;
      cancellation before confirmation has no side effects
- [x] positive and adversarial end-to-end tests cover a real oversized task, partial integration
      effort, source-preserving YAML, rollback at each phase and parity with ordinary graph views
- [x] the new command/tool is documented in HLD, README, help, changelog and facts with a complete
      migration example from a flat in-progress task
