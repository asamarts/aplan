## Why

`aplan add --tag cross-cutting` can create work outside every cut and `aplan mv --cut` can move a
task between cuts. There is no inverse operation that removes an existing member from its cut and
adds the reserved `cross-cutting` tag. One adopting repository hit the transition twice as work
changed shape, and had to edit both the milestone membership and the task front matter by hand.

Membership is already a multi-file invariant and `mv` already owns its checked mutation. Leaving
this one transition to a text editor buys no model boundary and makes the normal consequence of
learning during implementation the least safe move.

## Acceptance criteria

- [ ] one `mv` form moves a live task out of its cut and adds `cross-cutting` atomically
- [ ] the inverse move into a cut removes the reserved tag, so no task can be both a member and
      cross-cutting after a successful command
- [ ] terminal tasks, milestones, missing membership and concurrent edits are refused with the
      same post-state and compare-and-swap guarantees as existing `mv`
- [ ] a dry run or result names both edited files and the membership/tag transition
- [ ] CLI and MCP parity is decided explicitly if this mutation is exposed through agents
