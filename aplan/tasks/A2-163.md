## Why

`check-docs` treats any word shaped like the plan's own ids as a reference to this plan,
including near shapes: in a plan whose ids are `P1-nnn`, the word `P2-057` is reported as "not a
task in this plan, whose ids use `P1-`", with a did-you-mean when a close id exists. That is
right for a typo and wrong for a deliberate reference to another repository's plan. When one
plan's work moves into another, or two repositories cooperate, a document has to name the other
plan's tasks.

Reproducer: a plan with tasks `P1-001` and `P1-002`, and a document containing
`tracked in the other repository as P2-057`. `aplan check-docs` fails with one reference naming
no task. A Markdown link to the other repository's task file, a fenced block and a
`repository:id` form fail the same way. The only spellings that pass hide the id from search
(an HTML entity for the hyphen, or an underscore), which defeats the point of a reference.

The maintainers hit this while moving open work from one plan to another: older documents in the
first repository had to name the task in the second plan that now owns each item. A2-105
documents how a plan records a blocker in another repository, which is the same reference in a
different place, and A2-026 widens the shapes the scanner matches, which adds to the false
positives this removes; all three should agree on one form.

## Acceptance criteria

- [ ] a document can name another plan's id in a form the gate recognises as external (for example
      a declared external prefix in `.aplan.yml` bound to a repository, or a qualified
      `owner/repo#ID` form), and that id is not reported as missing from this plan
- [ ] a near-miss of this plan's own prefix that is not declared external is still reported, with
      its did-you-mean
- [ ] the external form is documented, and a test covers a passing external reference and a
      still-failing near miss
