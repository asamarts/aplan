## Why

When `add --from` refuses a batch after post-state validation, findings name the ids the entries
would have received. Atomicity means those ids do not exist: there is no task to `show`, file to
open or stable row to search. In one adopter's eight-entry batch, the author had to count entries,
and skipped entries made the minted number differ from the source index.

The future id is still useful, but it must be carried with the source subject the importer
actually judged: file, entry index and required title.

## Acceptance criteria

- [ ] every post-state finding caused by a manifest entry names that entry's source file, index
      and title as well as its prospective id
- [ ] skipped, explicit-id and generated-id entries cannot make the displayed index point at a
      different source object
- [ ] several failing entries retain deterministic input order and each finding carries its own
      subject rather than rediscovering one by id
- [ ] human and machine-readable refusals expose the same source identity
- [ ] a test puts the offending entry after a skipped entry so an id-derived index cannot pass
