## Why

When the terminal an `aplan tui` session runs in hangs up, the session should end the way
`Lifecycle::terminate` documents: SIGHUP is re-raised with its default disposition, so the parent
observes a hangup. It does not. On 87ec4cb (2026-11-18), a 120x40 pseudo-terminal whose controlling
side was closed four seconds after start gave the following:

- With stderr on the same terminal, the process exits with status 101, a panic. ratatui-core
  0.1.2's `Terminal::drop` reports a failed cursor restore with `eprintln!`, and `eprintln!` panics
  when stderr cannot be written.
- With stderr redirected to a file, it exits with status 2 after printing `Failed to show the
  cursor: Input/output error (os error 5)` and `aplan: terminal cursor restoration failed:
  Input/output error (os error 5); cleanup also failed: bracketed-paste: ..., mouse-capture: ...`.

After the hangup, writes to the terminal fail with `EIO`, so the screen loop or the mode restore
around it returns an error. `run_application` only re-raises a signal it still finds pending, so
it propagates that error and `Lifecycle::terminate` is never reached. A parent such as a shell,
`tmux` or an editor's terminal sees an error or a panic where it should see a hangup.

## Acceptance criteria

- [ ] a session whose terminal hangs up ends by SIGHUP's default disposition, whether stderr is the
      terminal or somewhere else
- [ ] restoring a terminal that has hung up is not reported as an error, and nothing panics while
      writing to a stderr that cannot be written
- [ ] a test drives the hangup through a pseudo-terminal and fails on the current behaviour
