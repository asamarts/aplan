## Why

An adopting repository authored 131 tasks that trace sections of a research document, and eight
anchors were rejected because the slug rule is not the obvious one. A heading of

```
### 4.4 Storage layout <U+2014> revised design
```

where `<U+2014>` stands for a literal em dash (written that way because this file follows the
plain-ASCII house style), slugifies to `44-storage-layout--revised-design`, with **two** dashes:
punctuation is removed and spaces become dashes, without collapsing the run the removed em dash
leaves behind. Generating anchors with the usual "collapse whitespace" assumption produces
`44-storage-layout-revised-design`, which resolves against nothing.

The failure is loud and the message is clear, which is what made the fix mechanical once the rule
was understood:

```
APLAN008 ABC-012: `traces` anchor `#44-storage-layout-revised-design` matches no heading
or table row in `docs/design-notes.md`
  fix: Add to `docs/design-notes.md` a heading, or a table row, whose text slugifies to
  `44-storage-layout-revised-design`; or correct the anchor to one the document already has.
```

So this is not a correctness problem. It is that an adopter writing anchors *in bulk*, which is what
authoring a plan from a research document is, has to discover the rule by failing. The reference
algorithm is recorded in `HLD.md` (section 5.4, the `APLAN008` slug algorithm), a design document,
but nowhere an adopter authoring `traces` would read.

## What has to be decided

Whether to document the rule, or to offer the slug. A `--format` on an existing command that
printed the anchors a document offers would make bulk authoring mechanical instead of
iterative; documenting the rule is much cheaper and probably enough.

## Why it is `untestable`

Placeholder until the shape is chosen, as above.
