## Why

An adopting plan declared a task ratified by a second task while also giving the ratifier a
preference to run after its subject. Generic reproducer:

```yaml
# ABC-001.md
ratified_by: [ABC-002]
# ABC-002.md
prefer_after: [ABC-001]
```

`ratified_by` prevents `ABC-001` from counting as done until `ABC-002` is done, while the preference
asks scheduling and presentation surfaces to put `ABC-002` after `ABC-001`. The hard dependency
graph remains acyclic and `aplan check` accepts the plan, but the two typed relationships jointly
recommend an impossible completion order.

This is not a generic cycle across one edge type. It is a cross-relation inversion whose
semantics are already known: a ratifier must be able to finish before its subject can count
as done. Diagnose it without turning `ratified_by` into a start blocker or making every
preference mandatory.

## Acceptance criteria

- [ ] `check` reports a dedicated actionable finding when task A names ratifier B and B
      directly or transitively prefers to run after A in a way that cannot be honored before
      A counts as done.
- [ ] A ratifier with no preference, a ratifier preferring an implementation prerequisite,
      and unrelated preferences remain valid; `ready` continues to ignore `ratified_by`.
- [ ] Unit and end-to-end fires/silent scenarios cover direct and transitive inversions,
      missing references, multiple ratifiers, and an ordinary preference cycle without
      conflating advisory order with `blocked_by`.
- [ ] Human, JSON, MCP, graph, and TUI surfaces identify both relationship paths and explain
      the repair: remove/reorient the preference or split implementation from completion.
- [ ] README, HLD, changelog, facts/behaviour compatibility, generated guidance, and upgrade
      notes document the new diagnostic and preserve ADR-0036 semantics.
