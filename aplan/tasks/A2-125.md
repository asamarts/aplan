## Why

One adopting repository supplied both directions of a live-plan blind spot. One task was delivered
across all three declared paths but remained `todo` and was offered by `ready` for five days.
Another declared valid, nonempty paths to the wrong subsystem and would discover that only when a
finished-work commit was refused by `close`. Aplan cannot infer completion or understand task
prose, and turning either signal into a rule would generate confident false positives.

A generic reproducer of the two shapes:

```text
ABC-001  todo  paths: [src/parser/**, src/lexer/**, docs/syntax.md]
               every entry changed in commits made after ABC-001.md was added
ABC-002  todo  paths: [src/billing/**]
               the work it describes is landing under src/invoices/** instead
```

Today `ready` offers both, and nothing a reviewer can run says that `ABC-001`'s entries all moved
after it was written or that `ABC-002`'s entry has not moved at all.

Aplan can expose those repository facts without making the inference. `aplan paths` already
measures how often the union of a task's paths matched a bounded recent history, while A2-092 will
expose the exact current-tree matcher. Extend the advisory measurement so a reviewer can see
activity per declared entry and relative to the task's own introduction, then decide whether the
task is done, not started, broad, stale or simply pointed at the wrong place. This reopens an
over-coverage question (a live task whose work has already shipped passes `check` and `verify`)
that was declined earlier because its measured candidate signals had no concrete subjects; the new
task and commits are concrete subjects, not permission to guess.

## Acceptance criteria

- [ ] one explicit `aplan paths` mode, or an equivalently discoverable advisory surface, reports
      per live task and per declared path entry which bounded commits matched and the latest match
- [ ] where history contains the task file's introduction, the report distinguishes path activity
      before and after that revision and can state exact facts such as "3 of 3 entries changed
      after this task appeared" without saying the task is complete
- [ ] union activity cannot hide a dead or inactive sibling entry; invalid, empty, broad and
      currently matching entries remain distinguishable and link to A2-092's exact matcher
- [ ] output labels all inferences as review prompts, never changes `check`, `verify`, `ready` or
      exit status, and does not parse prose or ask a model whether work is done
- [ ] a corpus measurement over the available adopting repositories counts useful, false-positive
      and unclassifiable prompts, broken down by broad shared paths, before choosing defaults or
      labels
- [ ] uncommitted/new tasks, shallow or bounded history, renames, merges, deleted paths, glob
      overlap, zero/one/many commits and an explicit historical revision have honest completeness
      states rather than confident zeroes
- [ ] human and versioned JSON output are deterministic and bounded; selection semantics match the
      existing `paths` command and performance does not become task-count-times-history
- [ ] regressions reproduce both cases above (a fully touched `todo` task and a task whose paths
      name the wrong place) plus a legitimately untouched future task and a broad shared path
      that must not be described as likely complete
