## Why

Optimizing `show` alone can leave the same loader and projection costs in `check`, `vacuity`,
`tasks`, reports, MCP resources or TUI refresh. A median can hide tail latency, redirecting stdout
can hide output cost, and a warm cache can hide a broken authoritative loader. The release claim
needs one derived inventory of every read-only command and adapter, with an explicit disposition
for local, repository, provider and output-dominated work.

The read-path performance design (`docs/design/read-path-performance.md`) defines a sub-100 ms p95
for bounded local reads, separates plan overhead from bounded Git work, and refuses to apply that
completion promise to explicit external refresh. It also requires work counters, because a shared
runner can make a wall-clock regression pass or fail for reasons unrelated to the code. This final
audit is where those separate proofs become one public claim.

The persistent plan snapshot's published 10,000-task exact-hit measurements, recorded in that
design, are the concrete scale handoff: despite zero YAML and trace parses, release p95 was
235.0 ms for `why`, 345.3 ms for `show --no-resolve` and 349.8 ms for `check` (development was
307.1/453.7/377.6 ms). Candidate enumeration, metadata observation, roughly 8.64 MB of JSON
decoding and per-command graph/projection remain O(n). This task must distinguish those
contributors before choosing a binary format, directory acceleration, owned graph index or another
mechanism; a zero-parse counter is not a latency pass.

## Acceptance criteria

- [x] a clap- and application-surface-derived inventory gives every read-only command, MCP
      resource and TUI read operation exactly one latency class and executable representative;
      missing, duplicate or stale entries fail
- [x] current, 1,000-task and 10,000-task corpora run in clean-checkout, exact-hit, one-edit,
      trace edit, config edit, corrupt-index and stale-observation states under release and
      development profiles
- [x] bounded local and structural reads meet sub-100 ms p95 on exact hits and one ordinary edit;
      repository reads report plan overhead separately, and external refresh is bounded,
      observable and explicitly excluded from the completion SLO
- [x] responses above the measured bound established by A2-136 start within 100 ms and stream with
      bounded memory; smaller human and machine responses complete within budget without changing
      stable bytes
- [x] deterministic counters ratchet files parsed/hashed, trace parses, graph/report builds,
      provider spawns and buffered bytes; the existing scale ratio gate remains independent and
      green
- [x] cache-disabled and cache-deleted runs execute the complete loader/validator corpus, while
      cache hit/miss/corruption results remain semantically identical across CLI, MCP and TUI
- [x] quiet-host and, when available, standard GitHub-hosted-runner measurements, dependency and
      binary-size effects and known hardware/filesystem limits are published; hosted timing
      remains observational and no contended-host result is presented as an absolute product
      budget
- [x] README, HLD, contribution/release guidance and the design record state the achieved
      contract, its output/provider exceptions and how to collect timing diagnostics
