## Why

`aplan check` is hermetic and fast: a **median of 70ms** over five runs on this project's plan at
237 tasks (2026-08-26), and 71ms over five runs at 242 tasks the next day. That number is the
argument for a local gate: it is faster than the editor save that triggered it, so there is no
reason for a plan to reach CI structurally broken.

The second measurement is there because it says something the first cannot: `check` is flat across
the plan's growth rather than merely fast once.

**The qualification this used to carry is closed.** It said that on plans with wide cuts the same
command took 835ms at 10,000 tasks and 16,880ms at 50,000, and that shipping a hook was an argument
for fixing that rather than a reason to wait for it. It was fixed, and not where this task expected:
a traversal asked for a node's blockers once per edge instead of once per node. At a shape of forty
cuts `check` now reads 36ms at 1,000 tasks, 308ms at 10,000, 768ms at 25,000 and 1,588ms at 50,000:
`O(n^0.97)` where it was `O(n^1.87)`, and flat in cut width where it was quadratic. So the premise
holds for large plans too, and the hook no longer ships with a caveat naming the plans it would be
switched off on.

There is no such gate, in either direction.

**An adopter has nothing.** `HLD.md` section 11 lists a `.pre-commit-hooks.yaml` beside the GitHub
Action ("since `check` is hermetic and fast enough to run on every commit"), and its distribution
section names pre-commit as a later channel. The file does not exist, and no task in this plan has
ever asked for it. So the one adoption path that costs an adopter three lines of YAML and no CI
configuration is the one that was specified and skipped.

**And this repository proved that documenting a hook is not shipping one.** `ci/githooks/pre-push`
was written, runs the development gate, and documents the exact command to turn it on. It had never
been turned on when this surfaced on 2026-08-26 while diagnosing two pushes that looked like CI
trigger failures: the runs were merely slow, but the investigation found that the only thing
standing between a red commit and `main` was somebody remembering to run `preflight.sh` by hand. The
maintainers' checkout now sets `core.hooksPath=ci/githooks`, and that repository-specific pre-push
gate has since been made fast and explicit. The remaining gap here is the shipped adopter-facing
pre-commit distribution, not enabling a second local hook for aplan itself.

Opt-in that nobody opts into is a plan for a gate, not a gate.

## What has to be decided

**Which command the hook runs, and the answer is only `check`.** `verify` opens the repository, and
with `--execute` it runs a test suite; neither belongs on every commit. The manifest ships the
hermetic half and says why the other half is CI's, or an adopter turns off a hook that got slow and
loses both.

**Whether the pre-commit framework is the only shape.** `.pre-commit-hooks.yaml` serves repositories
that already use `pre-commit`, which is a large audience and not everyone. A plain
`core.hooksPath`-installable hook covers the rest, and this repository is now its own first
consumer of that shape. Shipping one and documenting the other is a defensible split; shipping only
the framework manifest and calling adoption solved is not.

**Whether anything offers to install it, against ADR-0024.** That ADR settled that no command
recommends features and the guide answers instead. A distribution artefact is not a recommendation,
but an `aplan init` that offers to write a hook is the tool suggesting you run the tool more often,
which is close enough to the line that it should be decided here rather than discovered in review.

**The version has to be pinned, and there is already a gate for that.** `[workspace.package].version`
is the single source of truth for the version, and `ci/scripts/check-version-pins.sh` keeps the
install pins in the documents that instruct an adopter honest. A hook manifest carries a version, so
it joins that gate or it becomes the next string to drift.

## Acceptance criteria

- [ ] `.pre-commit-hooks.yaml` exists and an adopter gets `aplan check` on every commit by adding
      this repository to `.pre-commit-config.yaml`
- [ ] the manifest runs the hermetic command only, and says in one line where `verify` belongs
- [ ] a repository that does not use the `pre-commit` framework has a documented one-command
      install, which is the shape this repository now uses on itself
- [ ] the version in the manifest is gated against `[workspace.package].version`, not copied
- [ ] the HLD's references stop describing something that does not exist
- [ ] what the hook costs is stated where an adopter reads it, in terms of plan size rather than as
      one number, since the measurements above show that the number moves
