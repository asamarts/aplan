## Why

In plans whose task IDs encode the task's `phase` in their prefix (for example `P1-001` for phase
1 and `P2-001` for phase 2), `aplan add --phase 2` or `aplan add --cut <phase-2-cut>` mints the
next ID from the largest existing prefix series (`P1-NNN`) rather than the prefix matching the
task's phase, and `aplan check` accepts the prefix/phase mismatch without comment.

Once a mislabelled ID is committed and cited, renaming it is disruptive. `aplan` needs an explicit
decision on whether phase-carrying ID prefixes should be supported (for example via an opt-in
config declaration or prefix inference when every existing series is one-to-one with `phase`) or
documented as explicitly out of scope with a clear help note on `--id`.

## Acceptance criteria

- [ ] record the decision (opt-in phase-prefix mapping / deterministic inference vs. explicit
      non-goal) and its determinism/multi-family constraints
- [ ] if implemented, `aplan add` (CLI and MCP) mints the matching phase prefix and `check`
      reports mismatches; if declined as core behaviour, document the boundary clearly in `add`
      help and `docs/`
- [ ] tests pin the chosen behaviour on a multi-phase plan where the largest series belongs to a
      different phase than the target cut
