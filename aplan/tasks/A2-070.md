## Why

The generated agent block unconditionally prints `aplan check && aplan verify # what CI will run`,
and the Markdown roadmap footer says statuses are gated by `aplan verify` in CI. During a staged
adoption, one adopting repository had to generate both surfaces before it could complete binary
pinning and CI integration. The sentences turn target policy into false current-state claims in
outputs users and agents are told to trust.

The generator knows repository policy but cannot infer arbitrary CI wiring. It should describe the
required gate without asserting where it already runs, or make the claim conditional on explicit
configuration it can validate.

A build-toolchain contract (such as a declared MSRV) and a CI-integration claim are different
promises: nothing in toolchain work teaches the generator whether an adopter has wired `aplan` into
CI, which is the whole of this task. Once that adopter reaches CI integration it can no longer
demonstrate the defect, so the case rests on A2-071 and on the generator's own logic rather than on
one repository's current state.

## Acceptance criteria

- [ ] generated agent and roadmap output do not claim CI integration merely because an adopter
      requested them
- [ ] a repository that has explicitly configured aplan CI can still describe that enforced workflow
      accurately
- [ ] output fixtures cover both surfaces for a staged adopter and a fully gated adopter without
      requiring hand edits
- [ ] adoption documentation says when to generate the block and when CI enforcement becomes a
      proved claim
