## Why

An adopting repository lost an hour to an `APLAN018` that was telling the truth about the wrong
thing. Closing through the MCP tool stamped a fingerprint that `check` then rejected as drift, on
content byte-identical to the cited commit. The cause was two installations on one machine (the
server resolving `aplan` from the client's `PATH`, and the shell prepending another), and the
hashing changed between the two builds. That part is an environment fault and not this project's to
track.

**What is ours is that the two are indistinguishable by construction.** A fingerprint records a
hash and nothing about what computed it, so:

- `APLAN018` says the section changed and asks for a `git diff` that comes back empty. The reader
  either concludes the tool is broken or restamps without reading, **which is the habit the rule
  exists to prevent**.
- It is silent until it is expensive: a fingerprint stamped by one build fails the plan gate in CI
  pinned to another, on a section nobody touched.
- `aplan_close` returns `{"closed": ..., "unchecked": []}` with no version, so an agent told to
  prefer that surface learns nothing from the close about what it is talking to.

The adopter's report left this open as needing its own task if it was ever to be acted on. This is
that task.

## What has to be decided

**Whether the marker lives in the fingerprint or beside it.** In it is self-describing and changes
the stored form, which every closed task carries; beside it is a second field that can go missing.
Either way `check` gains one distinction it does not have: *stamped by a different build* is not
*the section changed*, and saying so is the whole value.

**Whether a version is the right marker.** A build ordinal answers "is this at least as new as the
one I stamped with"; a version string answers "which one", and `0.3.0-dev` names many builds. The
`facts` behaviour namespace (the named behaviours `facts --require` asserts) already exists for the
general form of this question, and a fingerprint marker should not become a second, weaker answer to
it.

**A stamp with no marker is not drift.** Every fingerprint already recorded predates this, so the
absent marker has to read as "unknown build", not as a mismatch: the same carve-out `APLAN028`
makes for tasks closed before drift detection existed.

## Acceptance criteria

- [x] a fingerprint stamped by one build and checked by another is reported as that, not as a
      changed section, and the message says what to do about it
- [x] a fingerprint with no marker is treated as unknown rather than as drift, so no closed task
      becomes a finding on upgrade
- [x] the agent surface reports the version that answered, so a client can tell what it reached
- [x] the reproduction is a test: stamp with one hashing, check with another, and see the right
      finding
