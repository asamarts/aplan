## Why

The public repository can build and attach one verified Linux artifact to a GitHub release, but it
does not publish the CLI to crates.io and has no complete transaction joining workspace package
publication, registry visibility, GitHub assets, and rerun behavior. The first public crates.io
release also has a one-time bootstrap constraint: trusted publishing can be configured only after
each new crate exists. Publish v0.5.0 without a long-lived CI secret, then leave a tested OIDC path
for every later release.

## Acceptance criteria

- [ ] the complete public increment is re-audited and all discovered release blockers are fixed
- [ ] v0.5.0 has one curated changelog section, release manifests, and a locked graph that agree
- [ ] every publishable workspace crate packages cleanly and publishes in dependency order
- [ ] publication waits for each internal crate to become resolvable before publishing dependents
- [ ] rerunning the workflow proves matching registry versions and assets instead of failing or
      silently replacing content with different bytes
- [ ] subsequent tag releases use crates.io trusted publishing from the protected GitHub release
      environment and retain no long-lived crates.io token in repository automation
- [ ] the exact tag source passes the complete local and hosted release profiles, and the installed
      crates.io CLI plus the GitHub release artifact both identify as v0.5.0
