## Why

`add.reads_a_task_list` identifies the original `add --from` seam and therefore passes on an older
build that rejects the later `body` field. One adopting repository depends on wholesale bodies and
can pin one exact binary, but cannot ask whether another build has this semantic capability. This is
a widening of an existing command and input format, the same reason the original batch behaviour was
named.

## Acceptance criteria

- [ ] `facts` exposes one stable behaviour name that means an `add --from` entry may carry a
      non-empty Markdown body which replaces the generated scaffold
- [ ] `facts --require <name>` distinguishes a build with batch bodies from the earlier
      `add.reads_a_task_list` build; requiring the old name alone remains backward compatible
- [ ] the behaviour's proof exercises the public command with a supplied body and its atomic failure
      boundary rather than only checking an internal parser
- [ ] `facts.json`, the capability documentation, and upgrading guidance describe why the original
      batch capability is insufficient for consumers that rely on bodies
