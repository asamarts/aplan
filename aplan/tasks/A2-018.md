## Why

The scheduled `scale` workflow has failed daily since 2026-11-11. Nothing in the source
changed; the failure starts exactly when the hosted `ubuntu-24.04` image moved from version
20261101 to 20261111. On the 10,000-task fixture, measured by
`tui_performance_gate_startup_interaction_and_memory`:

| metric (large, cold) | image 20261101 | image 20261111 | budget |
|---|---|---|---|
| first action | 59-73 ms | 545-547 ms | 250 ms |
| search | 578-786 ms | 5,516 ms | 2,500 ms |
| usable | 1.4-1.8 s | 3.6 s | 6 s |
| refresh | 1.6-2.2 s | 3.8 s | 6 s |

Search and the first action slowed about ninefold while startup and refresh only doubled, so
this is not a uniformly slower machine. Something on those paths reacts to the new image (a
subprocess, Git, the file system or the terminal), or the image exposes a latent slow path.

The maintainer decided (2026-11-17) that the cause is found before any budget moves.
Re-baselining a ninefold regression without understanding it would be a gate passing for the
wrong reason.

## Acceptance criteria

- [ ] the regression is reproduced on a controlled machine, and the slow operation is identified by
      profile or by bisecting the environment (for example Git, filesystem or terminal versions), with
      the measurements recorded
- [ ] if the cause is a code path, it is fixed and the existing budgets pass on the current hosted
      image without being raised
- [ ] if the cause is proven purely environmental, any budget change is recorded with the measurement
      that justifies it, in the test and in `docs/design/read-path-performance.md`
- [ ] the scheduled `scale` workflow passes on the current hosted image
