## Why

The scheduled `scale` workflow has failed daily since 2026-11-11 with no source change. Its logs
show two independent failures, not one regression that began with a new hosted image.

**Slower runners, 2026-11-11 to 2026-11-14.** The in-process render gate
`tui_performance_gate_render_interaction_and_graph_work` failed because a metric crossed its
budget by a few percent: `status_only_refresh_10000` at a p95 of 752-790 ms against 750 ms, or
`model_and_graph_10000` at 1.51 s against 1.5 s. Every in-process metric in those runs was about
35% slower than on 2026-11-06 to 2026-11-10. The first three ran on image 20261101.360.1, the image
of the passing runs; the fourth ran on 20261111.370.1. An equally slow runner passed on 2026-11-08
at 99% of the same budget. This is headroom, not a regression, and `A2-164` owns it.

**Fast runners on image 20261111.127.1, from 2026-11-15.** The in-process metrics are about 30%
faster than the baseline (`model_and_graph_10000` at 0.69 s against 0.87-1.02 s), and the render
gate passes. The end-to-end startup gate fails on the 10,000-task fixture, measured by
`tui_performance_gate_startup_interaction_and_memory`:

| metric (large, cold) | 2026-11-06 to 11-10 | 2026-11-15 to 11-17 | budget |
|---|---|---|---|
| first action | 59-76 ms | 545-547 ms | 250 ms |
| search | 578-813 ms | 5,493-5,516 ms | 2,500 ms |
| usable | 1.4-1.8 s | 3.5-3.6 s | 6 s |
| refresh | 1.6-2.2 s | 3.8 s | 6 s |

Across three days the action, search and refresh figures repeat to within 25 ms, so they are
deterministic rather than noise. One key that switches the view takes 545 ms, and the search,
which types about ten keys, takes 5.5 s: roughly 490 ms is added to each input event. On the same
runners the small and repository fixtures answer an action in 1-4 ms, and the in-process search
over 10,000 tasks takes 50 ms. The added cost therefore grows with the plan and is paid per event.
Startup and refresh also take about 2 s longer.

The maintainer decided (2026-11-17) that the cause is found before any budget moves.
Re-baselining a ninefold regression without understanding it would be a gate passing for the
wrong reason.

## Diagnosis (2026-11-18)

The unchanged code does not reproduce the failure on every hosted machine. A dispatched run of the
`scale` workflow landed on image 20261111.370.1 (AMD EPYC 7763 under Hyper-V, kernel
7.0.0-1017-azure), and the startup gate passed with the earlier figures: action 76 ms, search
801 ms, usable 1.8 s. The images name two fleets: every 20261111.127.1 runner seen was an Intel
Xeon 6975P-C under KVM with kernel 7.0.0-1014-aws, and every 370.1 runner an Azure machine.

A script drove the release binary in a PTY the way the gate does and read the main thread's
counters from `/proc` around each key. On the Azure runner and on a development machine, a key that
rebuilds the task list costs the main thread 70-110 ms of CPU, equal to its wall time. On a 127.1
runner (run 44280248089) the same keys cost 546-556 ms of wall time and the same CPU, while keys
that do not rebuild the list (`1`, `/`) took 1-2 ms. A key waits on nothing: at most 11 voluntary
context switches, at most 1,500 minor page faults, and no plan file read.

`perf record` over those keys on the 127.1 runner put 92.7% of the main thread's samples in
glibc 2.39's `__memmove_avx512_unaligned_erms`, and 93.3% inclusive under `Graph::ready_ranked`,
called from
`WorkDiscoveryWorkspace::project`. Every key that rebuilds the task list re-projects the work view,
which ranks the ready tasks again. The last step of that ranking, the `prefer_after` pass from
`A1-150`, placed tasks by removing each one from the front of a vector. With no preferences that is
still one shift of every remaining entry per task: on the 10,000 ready tasks of the large fixture,
about 2 GB of overlapping `memmove` per ranking. That runs in 70-110 ms on most machines and about
545 ms on the 127.1 machines, so the regression is in the runner fleet, while the cost it exposed
was in the code all along: quadratic in the number of ready tasks.

The fix keeps a min-heap of free positions and a count of each task's unplaced preferences, which
places tasks in exactly the same order in `O((n + e) log n)`.
`graph::ranking::the_preference_pass_matches_its_one_task_at_a_time_definition` compares it with
the original pass over 2,000 generated offers, and fails when the cycle fallback is changed.

Run 44282367585 built both versions on one 127.1 runner (Intel Xeon 6975P-C) and measured them
side by side. A key that rebuilds the list fell from 552-561 ms to 27-35 ms. With the fix, both
gates passed in that run with every budget unchanged. Against the scheduled runs that failed:

| metric (large, cold) | 2026-11-15 to 11-17 | with the fix | budget |
|---|---|---|---|
| first action | 545-547 ms | 28 ms | 250 ms |
| search | 5,493-5,516 ms | 299 ms | 2,500 ms |
| usable | 3.5-3.6 s | 1.0 s | 6 s |
| refresh | 3.8 s | 1.2 s | 6 s |

In the render gate, `model_and_graph_10000` reached a p95 of 0.72 s against 1.5 s and
`status_only_refresh_10000` 442 ms against 750 ms.

## Acceptance criteria

- [x] the regression is reproduced on a controlled machine, and the slow operation is identified by
      profile or by bisecting the environment (for example Git, filesystem or terminal versions), with
      the measurements recorded
- [ ] if the cause is a code path, it is fixed and the existing budgets pass on the current hosted
      image without being raised
- [ ] if the cause is proven purely environmental, any budget change is recorded with the measurement
      that justifies it, in the test and in `docs/design/read-path-performance.md`
- [ ] the scheduled `scale` workflow passes on the current hosted image
