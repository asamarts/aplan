## Why

An adopting repository arrived with its own audit script already validating the DAG, unique ids,
unknown references and status transitions. `aplan` validates four of those and adds the evidence
gate the incumbent lacks, so adopting means running both until the overlap is retired, and nothing
written down addresses that state.

**The hazard is disagreement rather than duplication**: two tools deriving a DAG from one source,
differing on a cycle or a dangling reference, with no procedure for which is right. That adopter's
own answer was to require a commit where both agree on the same tree before the incumbent's graph
validation is deleted, and that procedure is the adopter's invention rather than anything this
project offered.

Another adopter was pointed at a plan document before migration; this is the adjacent case, a plan
with an *incumbent checker*, and it is the commoner one for a repository mature enough to want an
evidence gate.

## What to decide

Where it goes, and how much of it is a procedure rather than prose. The useful shape is the one
the adopter invented: run both, require a commit where they agree on the same tree, then delete
the overlap. Naming that as the supported path costs a section.

## Testing note

A documentation fix has no test that would fail if reverted unless it carries an executable
recipe, which this one may. Whether this task needs an `untestable` exemption is decided with its
shape.

## Acceptance criteria

- [ ] an adopter with an existing linter is told how to run both and how to know when to stop
- [ ] the disagreement case is named, since that is the hazard rather than the duplication
