## Why

Found in an adopting repository. A task was parked (`blocked` with `revisit_at`) until a scheduled
run; when the owner released it, `aplan start` moved it to `in_progress` and left `revisit_at` in
place, so the next `aplan check` reported `APLAN042` ("carries `revisit_at` and is `in_progress`
... nothing reads it here"). The agent deleted the field by hand.

Generic reproducer: `ABC-001` has `status: blocked` and `revisit_at: 2026-12-01T00:00:00Z`.
`aplan start ABC-001` succeeds, and `aplan check` then reports `APLAN042` for `ABC-001`.

`aplan unpark` would have cleared it: it returns parked work to `todo` and clears `revisit_at`.
Nothing on the agent's path named it. `start` takes a `blocked` task without a word about
`unpark`, and `APLAN042`'s instruction says to "drop the `revisit_at`" without naming the command
that does. `work.rs` keeps a misplaced value on purpose so that it does not silently disappear,
and that is right for a value someone typed onto the wrong status, not for one a transition
aplan made left behind.

## Acceptance criteria

- [x] decided: `start` on a parked task refuses and names `unpark`, or does what `unpark`
      does (clears `revisit_at`) and says so; or it keeps today's behaviour and `APLAN042`'s
      instruction names `unpark`.
- [x] whichever it is, a test pins it, and the CHANGELOG says so if behaviour changes.
