## Why

Reported in #21. `aplan start` succeeds on a task whose `paths` match nothing tracked, and
`verify` then fails on it at once with `APLAN053` under `deny_warnings`. That is the normal
state when a task's first act is to create its files, so an agent following the documented
loop hits a failure straight away. The rule's own fix text makes it worse: it says that when a
task owns files that do not exist yet, "the status is the thing to change", which tells the user
to stop a task they have just started.

## Acceptance criteria

- [ ] `start` stays exit 0 and prints a note when `APLAN053` would fire right now, in the words
      #21 proposes: "nothing tracked matches this task's `paths` yet, so `aplan verify` will report
      APLAN053 until its files are added"
- [ ] `APLAN053`'s fix text no longer tells a just-started task whose files do not exist yet to
      change its status
- [ ] the note reads the same tracked paths `verify` reads
- [ ] MCP `aplan_start` returns the same note in its result, since it starts tasks by its own path
- [ ] #21 is closed
