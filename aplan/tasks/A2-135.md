## Why

`vacuity` currently discovers whether a configured switch changes enforcement by constructing
modified options and running complete validation again. That keeps it tied to the real rule set,
but also rebuilds graph state and can reopen trace documents for each relevant switch. On the
pre-public plan of several hundred tasks, an optimized `vacuity` took about 461 ms, even though
its answer is a projection of which checks were enabled and which produced findings during the
same structural evaluation.

Replacing the repeat passes with a hand-maintained list would be faster and unsafe: a new rule or
configuration switch could silently be omitted. The validation catalogue must drive typed
activation observations so a new member cannot compile or pass the executable audit without a
vacuity disposition.

## Acceptance criteria

- [x] one validation pass emits typed activation observations sufficient to distinguish an enabled
      check with no findings, an enabled check with findings, a disabled check and an inapplicable
      check without re-evaluating the plan
- [x] the rule/configuration catalogue drives the mapping; missing, duplicate and stale switch
      dispositions fail an executable exhaustive audit
- [x] `vacuity` performs one graph construction and at most one parse of each trace document for
      one snapshot, proved by deterministic work counters rather than elapsed time alone
- [x] human and machine output, ordering and exit semantics remain byte-compatible for the
      existing corpus, including absent config, explicitly disabled checks and multiple rules
      behind one key
- [x] a mutation test that restores the repeated validator path fails the work-count proof, and
      cache-disabled measurements record the resulting current- and generated-plan improvement
