## Why

`docs/upgrading.md` recommends asserting a capability rather than a version, and gives the flag to
do it:

> **Prefer asserting a capability over a version.** [...] Assert it rather than searching for it:
> `aplan facts --require test.covers --require APLAN024 --require tasks`

A reader following that advice writes the key they remember. Config keys are dotted, and the leaf is
what sticks:

```console
$ aplan facts --require require_min_strength
aplan 0.3.0 does not advertise:
  require_min_strength
It advertises 185 others; `aplan facts` lists them.
```

The key is `evidence.require_min_strength`, and it is advertised. Loading `.aplan.yml` handles the
same mistake differently:

```console
$ aplan check
aplan: loading .aplan.yml: unknown key `requre_effort` (did you mean `require_effort`?)
```

Two surfaces, one class of mistake, and only one of them helps. `--require` is the surface on the
upgrade path, where the reader is least sure what this build calls things.

## What makes it worth fixing rather than documenting

The advice in `docs/upgrading.md` is to put this flag in a `Containerfile` or a CI step, where it is
written once and read when it fails. "Does not advertise `require_min_strength`" against a build
that does advertise `evidence.require_min_strength` reads as a missing capability, and the
documented next move (stage a newer binary) is wrong and will not help. `docs/upgrading.md` already
records a hand-written version of this check telling an operator a binary lacked a key it supports.

A suggestion is cheap here: the candidate set is `config_keys` plus rules, commands, formats,
evidence kinds, behaviours and MCP tools, all of which this command already has in hand, and a
unique suffix match after the last `.` would have answered this one outright.

## Acceptance criteria

- [ ] a `--require` miss that is close to a real capability names the capability it is close to,
      the way an unknown config key does
- [ ] a leaf that uniquely identifies one dotted key is treated as close: `require_min_strength`
      finds `evidence.require_min_strength`
- [ ] a miss that is close to nothing still says so plainly, and the exit codes do not move: 1 for
      a build that answers no, 2 for one too old to be asked

## Notes

Found by an adopting repository on `v0.3.0`, while moving its container build check from a version
grep to `facts --require`, which is the change `docs/upgrading.md` asks for.
