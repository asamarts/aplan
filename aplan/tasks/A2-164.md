## Why

The scheduled `scale` workflow failed from 2026-11-11 to 2026-11-14 in the in-process render gate
`tui_performance_gate_render_interaction_and_graph_work`, with no source change. Each time one
metric crossed its budget by a few percent:

| run | `status_only_refresh_10000` p95 | `model_and_graph_10000` p95 | result |
|---|---|---|---|
| 2026-11-08 | 741 ms (99%) | 1.37 s (91%) | passed |
| 2026-11-11 | 756 ms (101%) | 1.39 s (92%) | failed |
| 2026-11-12 | not reached | 1.51 s (101%) | failed |
| 2026-11-13 | 752 ms (100%) | 1.38 s (92%) | failed |
| 2026-11-14 | 790 ms (105%) | 1.42 s (95%) | failed |
| 2026-11-18 | 729 ms (97%) | 1.34 s (89%) | passed |

The budgets are 750 ms and 1.5 s, and `graph_window_traversal_sparse` sits at 83-87% of its own.
On those days every in-process metric was about 35% slower than on 2026-11-06, 11-07, 11-09 and
11-10, uniformly, which is the spread between the hosted machines GitHub assigns, not a regression
in aplan. The same image produced passing runs on faster machines. A budget that a slower assigned
machine exceeds by chance makes the scheduled run red for no reason in aplan, and hides a real
failure among the false ones.

The scheduled run of 2026-11-18 (44309492022) landed on another slow machine, an Azure runner on
image 20261116.376.1. It passed with 21 ms to spare on `status_only_refresh_10000`, and
`graph_window_traversal_sparse` was at 80% of its budget. It included the `A2-018` fix, which does
not account for these figures: on the 20261111.127.1 runners `model_and_graph_10000` had a p95 of
0.70-0.72 s in the scheduled runs before the fix and 0.72 s in run 44282367585 with it.

`A2-018` separated this from the large-fixture startup regression it diagnoses, which is a
different failure on different machines.

**Decision (maintainer, 2026-11-18): the reference host owns the wall-clock budgets.** This
supersedes the decision of the same day to calibrate per run. The three wall-clock gates (the
in-process render gate, the layered-graph gate, and the real-terminal startup and interaction
gate) are judged on the maintainer's quiet reference host, which runs one benchmark at a time
through a queue. A script builds and measures inside one queue slot, pinned to one CPU, once the
host's load has fallen to 0.25 or less, and the budgets are re-based on what it measures. The
hosted nightly `scale` run keeps printing every metric, keeps its memory and work-count checks,
and fails a wall-clock metric only past 1.5 times its budget of 2026-11-18, which catches a gross
regression without failing on a slow machine. The reference gate runs before every release and
for any change to the TUI's render or model code. ADR-0065 stands: no runner is registered for
this repository, and the reference host is reached by a script, not by a workflow. Calibrating
per run was dropped because the hosted fleets differ by about 35%, and a reference workload would
have to measure a machine's speed more precisely than that to tell a slower machine from a
regression.

**Acceptance agreed in advance (maintainer, 2026-11-18).** Five runs on the reference host, each
in its own queue slot, pinned to one CPU at a load of 0.25 or less. Every metric's p95 varies by
at most 5% across the five runs, or by at most 0.1 ms for a metric under 2 ms. Each budget is the
worst p95 observed times 1.25. A deliberate doubling must fail the gate. If any part fails, the
work stops and the measurements go back to the maintainer.

The never-merged branch `diag/a2-018-hosted`, which can dispatch the diagnostic runs on the hosted
fleets, is kept until this task closes and is deleted then.

**Measured (2026-11-19).** Five runs on the reference host, each in its own queue slot and pinned
to CPU 2 at a load of 0.20 to 0.25, measured all 74 wall-clock metrics of source
`58025c81b7ad-0d81d7890265-32f79219ed53`. `docs/design/read-path-performance.md` records every
metric's range, spread and budget. 68 agreed within the spread agreed in advance, among them
`model_and_graph_10000` (1.4%) and `status_only_refresh_10000` (2.7%). Six did not:
- `graph_focus_sparse`, `graph_focus_fan_in` and `graph_focus_crossing` spread 9 to 11%, or 0.2 ms,
  between runs, but under 1% within one;
- the real-terminal first feedback of the repository fixture, cold and warm, and of the large
  fixture, cold, spread 5.4 to 6.4%, or 0.4 ms on about 7 ms.

As agreed, the work stopped there and the measurements went to the maintainer.

**Decision (maintainer, 2026-11-19): the six keep the hosted rule.** The metrics that agree get
reference budgets. The six that do not are held on the reference host too to 1.5 times their
hosted budget, the rule of a hosted run, until `A2-180` makes them measurable there. The agreed
rule is not loosened after the fact to admit them.

**Decision (maintainer, 2026-11-19): a budget is at least the worst p95 plus 0.1 ms.** Ten
metrics are under 0.4 ms: seven hit tests of 76 to 126 ns, a 9 ns progress tick and two paints.
For them, the worst p95 times 1.25 gives budgets that an unrelated change in code layout can
exceed. The floor mirrors the agreed allowance of 0.1 ms for small metrics, and leaves every other
budget at the worst p95 times 1.25.

**Proven (2026-11-19), with one false failure.** Four runs with `--budgets reference` followed,
each in its own slot:
- **The first run, on the commit that added the budgets, failed one metric.**
  `pty_small_cold_feedback` read 9.70 ms against its 9.17 ms budget, where it had measured
  7.20 to 7.34 ms. One of its three launches was slow.
- **The first doubling run passed, which exposed a bug in the script.** That commit was older
  than the previous run's build, and `git archive` stamps each file with its commit's time, so
  cargo reused the previous binary. The script now extracts with the time of extraction.
- **With that fix, the commit with the budgets passed twice.** The doubling commit failed exactly
  `model_and_graph_10000` (3.26 s against 2.075 s) and `status_only_refresh_10000` (1.85 s
  against 1.154 s), and still printed all 80 metrics.

**Decision (maintainer, 2026-11-19): every first feedback keeps the hosted rule.** All six
real-terminal first-feedback metrics are about 7 ms and the slowest of three launches. Three were
already among the six that did not agree, and another produced the one false failure. They join
the hosted rule and `A2-180`. That leaves 65 metrics with reference budgets and nine on the hosted
rule.

## Acceptance criteria

- [x] a script builds and runs the three wall-clock gates on the reference host inside one queue
      slot, pinned to one CPU once the load is 0.25 or less, and brings back every metric
- [x] five such runs are recorded, and each metric whose p95 varies across them by at most 5%, or
      by at most 0.1 ms under 2 ms, has a reference budget. The six that vary more, and every
      first feedback, keep the hosted rule on the reference host and went to `A2-180`, by the
      maintainer's decisions of 2026-11-19
- [x] each reference budget is the worst p95 of those runs times 1.25, and at least the worst p95
      plus 0.1 ms. The gate applies them when it runs on the reference host, and
      `docs/design/read-path-performance.md` records each budget and its basis
- [x] a deliberate doubling of `status_only_refresh_10000` or `model_and_graph_10000` fails the
      reference gate
- [x] the hosted `scale` run prints every metric and fails a wall-clock metric only past 1.5
      times its budget of 2026-11-18, with its memory and work-count checks unchanged
- [x] ADR-0067 records that the reference host owns the wall-clock budgets, and the release task
      requires the reference gate to pass on the release revision
- [x] the branch `diag/a2-018-hosted` is deleted
