## Why

The scheduled `scale` workflow failed from 2026-11-11 to 2026-11-14 in the in-process render gate
`tui_performance_gate_render_interaction_and_graph_work`, with no source change. Each time one
metric crossed its budget by a few percent:

| run | `status_only_refresh_10000` p95 | `model_and_graph_10000` p95 | result |
|---|---|---|---|
| 2026-11-08 | 741 ms (99%) | 1.37 s (91%) | passed |
| 2026-11-11 | 756 ms (101%) | 1.39 s (92%) | failed |
| 2026-11-12 | not reached | 1.51 s (101%) | failed |
| 2026-11-13 | 752 ms (100%) | 1.38 s (92%) | failed |
| 2026-11-14 | 790 ms (105%) | 1.42 s (95%) | failed |
| 2026-11-18 | 729 ms (97%) | 1.34 s (89%) | passed |

The budgets are 750 ms and 1.5 s, and `graph_window_traversal_sparse` sits at 83-87% of its own.
On those days every in-process metric was about 35% slower than on 2026-11-06, 11-07, 11-09 and
11-10, uniformly, which is the spread between the hosted machines GitHub assigns, not a regression
in aplan. The same image produced passing runs on faster machines. A budget that a slower assigned
machine exceeds by chance makes the scheduled run red for no reason in aplan, and hides a real
failure among the false ones.

The scheduled run of 2026-11-18 (44309492022) landed on another slow machine, an Azure runner on
image 20261116.376.1. It passed with 21 ms to spare on `status_only_refresh_10000`, and
`graph_window_traversal_sparse` was at 80% of its budget. It included the `A2-018` fix, which does
not account for these figures: on the 20261111.127.1 runners `model_and_graph_10000` had a p95 of
0.70-0.72 s in the scheduled runs before the fix and 0.72 s in run 44282367585 with it.

`A2-018` separated this from the large-fixture startup regression it diagnoses, which is a
different failure on different machines.

**Decision (maintainer, 2026-11-18): calibrate per run.** Each run times a fixed reference
workload on the machine it was given and scales the render budgets by that machine's speed,
within stated bounds, so a slower machine is judged against what it can do and a real regression
still fails. Before relying on it, the calibration's own noise is measured on both hosted fleets
(the AWS `20261111.127.1` machines and the Azure ones); if it is too noisy to separate a machine's
speed from a regression, the choice goes back to the maintainer rather than ahead with wider
budgets. The never-merged branch `diag/a2-018-hosted`, which can dispatch the diagnostic runs on
the hosted fleets, is kept until this task closes and is deleted then.

## Acceptance criteria

- [ ] the calibration's noise is measured on both hosted fleets and recorded, and the maintainer
      has agreed, in this task, that it is quiet enough before the budgets depend on it
- [ ] the render gate scales its budgets by a per-run reference workload, within stated bounds,
      and the decision records the measurements from the slower and faster runners it is based on
- [ ] the gate passes on the slower runners and still fails a real regression: a deliberate
      doubling of `status_only_refresh_10000` or `model_and_graph_10000` fails it
- [ ] `docs/design/read-path-performance.md` records each changed budget and its basis
- [ ] the branch `diag/a2-018-hosted` is deleted
