## Why

The scheduled `scale` workflow failed from 2026-11-11 to 2026-11-14 in the in-process render gate
`tui_performance_gate_render_interaction_and_graph_work`, with no source change. Each time one
metric crossed its budget by a few percent:

| run | `status_only_refresh_10000` p95 | `model_and_graph_10000` p95 | result |
|---|---|---|---|
| 2026-11-08 | 741 ms (99%) | 1.37 s (91%) | passed |
| 2026-11-11 | 756 ms (101%) | 1.39 s (92%) | failed |
| 2026-11-12 | not reached | 1.51 s (101%) | failed |
| 2026-11-13 | 752 ms (100%) | 1.38 s (92%) | failed |
| 2026-11-14 | 790 ms (105%) | 1.42 s (95%) | failed |

The budgets are 750 ms and 1.5 s, and `graph_window_traversal_sparse` sits at 83-87% of its own.
On those days every in-process metric was about 35% slower than on 2026-11-06, 11-09 and 11-10,
uniformly, which is the spread between the hosted machines GitHub assigns, not a regression in
aplan. The same image produced passing runs on faster machines. A budget that a slower assigned
machine exceeds by chance makes the scheduled run red for no reason in aplan, and hides a real
failure among the false ones.

`A2-018` separated this from the large-fixture startup regression it diagnoses, which is a
different failure on different machines.

## Acceptance criteria

- [ ] the decision states how the render gate tolerates the hosted machines' spread, with the
      measurements from the slower and faster runners it is based on
- [ ] the gate passes on the slower runners and still fails a real regression: a deliberate
      doubling of `status_only_refresh_10000` or `model_and_graph_10000` fails it
- [ ] `docs/design/read-path-performance.md` records each changed budget and its basis
