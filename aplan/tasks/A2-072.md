## Why

Found while making the plan's release concept carry the version it produced (ADR-0038). A release
node tagged `release` and `v1.0.0` renders:

```
release (release)  a release  [todo]  ...
```

`cut_label` takes the first tag that parses as a cut version, else the first tag that is not
`milestone`. `parse_cut_version` reads `vN.N` only, so `v1.0.0` does not parse, and the fallback
picks `release` (the marker tag) as the label.

Two things are wrong and they are separable. The label falls back to a tag that is a *marker*
rather than a name, the same class as `milestone`, which is already excluded. And a release's
version is `vN.N.P` by nature, which the cut-version parser was never asked to read, so releases
cannot sort numerically the way cut versions already do.

ADR-0038 decides that a release carries its version in a field rather than a tag, which removes
the *need* for this path but not the defect: a plan that tags a release `v1.0.0` today gets a row
labelled `release`, and nothing says so.

## Acceptance criteria

- [ ] a release node does not render a marker tag as its label
- [ ] `vN.N.P` either parses and sorts with `vN.N`, or is refused with a message saying which
      vocabulary a cut tag uses
- [ ] whichever is chosen, a plan mixing `v0.9` cuts and a `v1.0.0` release orders correctly
