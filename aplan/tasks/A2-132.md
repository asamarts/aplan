## Why

An adopter's failed release gate exposed a graph transition that no current supported command can
express atomically: a failed gate must preserve the outcome, park or drop incompatible successor
work, add replacement or terminal-publication tasks, and rewire dependencies before any default
successor becomes ready. `add --from` atomically creates work, `drop` records one terminal
decision, and `dep apply --from` atomically rewrites dependencies, but composing them as separate
commands leaves a valid yet semantically partial graph after interruption.

For example, gate `ABC-001` fails. Its publication successor `ABC-002` must be dropped with a
reason, a remediation task `ABC-003` must be added, and the release milestone `M-one` must be
rewired to wait on `ABC-003`. Today that takes at least three commands (`drop`, `add --from`,
`dep apply --from`), and an interruption between them leaves a semantically partial transition in
the repository.

This is not a conditional dependency language or a workflow engine. The gate reviewer still
decides the concrete post-state; aplan only applies that explicit mixed transition as one
previewed, validated change. Unrelated concurrent edits are outside the transaction and must
conflict rather than be absorbed.

A second adopter supplied the single-decision control: ordinary `drop --cut` records the terminal
status, then asks the author to write the reason into prose in a second operation, because aplan
deliberately keeps that prose out of the status model. This task closes the interruption window
for a larger review by carrying the explicit reason in the same all-or-nothing transition
manifest.

## Acceptance criteria

- [ ] A documented batch surface can combine new task creation, live-task drop/park decisions with
      reasons, dependency add/remove, cut membership moves, and tag changes against one
      identified plan snapshot.
- [ ] The batch previews exact files and semantic effects, validates the requested final plan
      once, and publishes all files or none with compare-and-swap protection; a state invalid only
      in an intermediate ordering can succeed when the final state is valid.
- [ ] `done` and evidence-bearing closure remain outside the batch unless the ordinary close
      evidence gate is invoked; settled-cut, terminal-history, unknown-ID, conflict, cycle,
      tag-cardinality, and missing-membership violations refuse the complete transaction.
- [ ] A failed-gate fixture drops or parks the incompatible successor, creates a reachable
      remediation or terminal-publication path, and proves the default release path is never
      transiently ready; interruption and write-failure fixtures leave the original graph
      byte-identical.
- [ ] CLI, application boundary, HLD, facts, changelog, dry-run, and machine output distinguish
      this explicit plan transition from hidden conditional dependencies and from the
      dependency-only `dep apply --from` batch.
