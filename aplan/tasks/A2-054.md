## Why

A large adopting repository reported the same sequence three times. `show <ID>
--refresh-evidence --require-current-evidence` (or `close --execute`) executed the configured
test citations and reported every one current, publishing an observation. The very next
plain `show <ID>` kept the same observation id and timestamp but listed every citation as
`stale, unavailable`, with the reason "a provider, environment, executable, or declared
material input changed".

In at least one case the closure itself rewrote the task file, which the repository listed
among its declared material inputs, so the observation was invalidated by the command that
produced it. Whether or not that explains every case, a user who has just proved a citation
current is told it is stale with no change of their own, and repeats whole-plan replays that
take minutes.

## Acceptance criteria

- [x] the sequence is reproduced in a fixture: a task-scoped refresh or `close --execute` followed
      immediately by `show` on an unchanged tree
- [x] an observation is not invalidated by a write the producing command made itself, or the stale
      reason names the exact input that changed
- [x] a test pins the corrected behaviour for both `show --refresh-evidence` and `close --execute`
