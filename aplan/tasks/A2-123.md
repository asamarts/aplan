## Why

ADR-0029 correctly keeps `blocked_by`, cuts, cycle detection and rollups inside one repository.
A blocker in a sibling repository is therefore encoded locally, and A2-105 is to document that
encoding as a recipe: a local proxy plus prose and a dated revisit. That recipe has now failed
twice in adopting repositories. In one, a task stayed parked for weeks after its upstream work
shipped. In another, a live dependency on a task in a sibling repository has a terminal state
that can be checked deterministically in a pinned, validated checkout, but the local proxy still
needs a person to run that check and unpark it.

This is stronger evidence than a request for a distributed plan graph. Decide whether a narrower
external readiness condition can be resolved like evidence while leaving the local graph local.
Compare the current proxy, URL evidence, imported attestations, pinned plan snapshots and a
trusted resolver before committing to a new field, and keep the architecture decision separate
from any conditional implementation work.

## Acceptance criteria

- [ ] an ADR records the two measured adopter cases (a proxy left parked after upstream delivery,
      and a deterministically checkable upstream terminal state that still needed a manual
      unpark) and compares manual proxy, URL evidence, imported attestation, pinned snapshot and
      trusted external-condition resolver
- [ ] the decision states whether a read-only external predicate can affect readiness without
      becoming a remote `blocked_by` node, cut member, closure citation, status transition,
      cross-repository cycle or distributed transaction
- [ ] any accepted declaration has an opaque stable identity, exact subject and predicate in task
      data while executable resolution, credentials and trust policy remain outside pull-request
      controlled content
- [ ] `check` stays hermetic; the design assigns satisfied, false, unavailable, unconfigured,
      malformed, stale, moved-revision and identity-mismatch states consistently to `verify`,
      `ready`, `why`, structured output, MCP and the TUI
- [ ] reproducibility requirements name immutable upstream revision/content identity, resolver
      identity, bounds and observation time; a mutable branch, reachable URL or copied remote
      status cannot silently satisfy the condition
- [ ] credential isolation, redaction, redirects, timeouts, malicious output, offline operation,
      upstream regression and local task-id collision have explicit fail-closed semantics
- [ ] if accepted, create bounded implementation and two-repository conformance tasks rather than
      hiding them behind this decision; if rejected, strengthen A2-105's tested manual proxy with
      a pinned detached-checkout probe and short revisit interval

## Why it is `untestable`

This task decides an architecture boundary and decomposes or rejects a feature. Later fixtures can
prove an accepted resolver and documentation can preserve a rejected recipe, but neither proves
that the trust and repository-boundary tradeoff itself is the right one.
