## Why

ADR-0037 made the generated `AGENTS.md` block identify the build that wrote it and widened
`APLAN041` to report a different writer even where repository policy had not moved. One adopting
repository has measured the consequence rather than predicting it: its stamp flipped six times in
four days between legitimate development builds, reached a state no installed binary could
reproduce, and made a first-time contributor create and then revert a commit after the diagnostic
told them to regenerate with the wrong build. A second adopter separately confirms the good half:
a runner configuration change moves the policy-derived block, and the exact regeneration
instruction is useful.

The problem is wider than one comment line. The generated block also enumerates the running
build's MCP tools, so two capable builds can produce different bodies from one unchanged plan. A
byte gate cannot simultaneously require both. `advisory: [APLAN041]` turns a recurring false gate
into a recurring warning and does not answer which bytes belong in the repository.

Separate repository-policy drift from generator provenance and live tool capability. Preserve the
rule's ability to catch stale policy while ensuring an arbitrary `aplan` earlier on `PATH` cannot
make an otherwise correct contract uncommittable. Coordinate the answer with A2-081, which owns
declaring the build a plan requires; do not invent ordering between opaque surface digests.

A third adopter supplies the complementary policy case: the same build-only mismatch was useful as
an advisory during an unrelated audit, both gates passed, and the adopter deliberately retained it.
The fix must narrow the blocking contract rather than erase provenance or silence the diagnostic;
repositories that choose an advisory policy should keep receiving the actionable signal.

A fourth adopter reproduced the blocking form between delivery and its first audit: repository
policy was unchanged, but adding a build capability moved the surface digest and made the
generated contract fail before structural validation. Pinning a released build would reduce the
frequency, but would not separate policy from build identity; that is why this work belongs here
while the authoritative-build decision remains the prerequisite in A2-081.

## Acceptance criteria

- [x] a new ADR supersedes ADR-0037 only where it made writer identity or the checking build part
      of the repository-policy verdict, and explicitly separates policy content, live capability
      and provenance
- [x] two builds rendering the same policy no longer alternate a blocking committed file merely
      because their version, source, binary or surface identity differs
- [x] a real policy change, including runner configuration and any build-independent agent
      instruction derived from it, still fires `APLAN041` and retains an exact repair
- [x] build-specific MCP capability is either discovered from the serving process or bound to an
      explicitly declared required build; a generated block never promises tools the selected
      server lacks and never requires every valid build to publish one identical catalogue
- [x] the diagnostic never tells a reader to regenerate with the currently running build when that
      can make the authoritative gate worse; where a build choice matters it names both known
      identities and the documented pin/require route
- [x] provenance remains available for diagnosis without being mistaken for semantic drift, and
      malformed or duplicate provenance lines are not silently normalized away
- [x] regressions exercise policy-only drift, provenance-only drift, capability-only drift, a
      first-time contributor on an unpinned `PATH`, and two same-version development builds
- [x] the narrowed meaning of existing `APLAN041` has a `Behaviour` and proof; changelog and
      upgrade guidance retire the mixed-build advisory/regeneration workaround where the new
      contract makes it unnecessary
