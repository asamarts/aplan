## Why

"Building a stageable binary" in `docs/upgrading.md` documents a containerized musl build for
adopters who need an unreleased aplan. One adopter followed it and produced a static,
digest-pinned binary, but the recipe mounts the current working tree (`-v "$PWD":/src`). On a
shared checkout that can compile another session's uncommitted Rust and produce an artifact no
commit reproduces. The container also sees no `.git`, so `facts --identity` correctly omits
`source`; an external table in the adopter's README becomes the only claim connecting artifact and
revision.

The safe unit is an immutable Git tree, not a read-only view of mutable files. Replace the recipe
with an export or detached checkout of an exact commit, pass that source revision explicitly when
Git metadata is absent, isolate build output, and verify the produced identity before staging it.
Do not turn that adopter's one byte-for-byte repeat into a general reproducible-build promise:
compiler, container and dependency inputs still matter.

## Acceptance criteria

- [ ] the supported staging recipe resolves and records one full source commit before building and
      never mounts a shared dirty checkout as though it were that revision
- [ ] an archive/detached source without `.git` sets `APLAN_SOURCE_REV` to the validated commit,
      and the resulting `facts --identity` is checked for source, capability and binary digests
      before the artifact is copied into a consumer image
- [ ] build output and caches cannot modify the immutable source tree, and shell examples handle
      spaces, cleanup, failures and architecture explicitly without relying on ambient `PWD`
- [ ] the guide distinguishes source identity, binary identity, static portability and
      reproducible compilation; it does not promise identical bytes without pinning every relevant
      build input
- [ ] README, upgrading guidance and CI staging guidance point to one canonical procedure, and the
      prior working-tree command is removed or labelled unsafe rather than left as a second route

## Why it is `untestable`

This task corrects deployment documentation. Existing identity and build tests prove the fields
and artifact behavior, but a workspace test cannot prove an adopter used an immutable external
checkout or pinned the container/toolchain it chose.
