## Why

`aplan init` created `.aplan.yml` with `root: aplan` implied and no plan directory. One adopting
repository then dry-ran its first wholesale add. Every row targeted `aplan/<id>.md`, not the
`aplan/tasks/<id>.md` shape used in the README and in aplan's own repository.

The current rule is documented: write to `<root>/tasks` when that directory exists, otherwise to
the root. The awkward part is that an empty `aplan/tasks` directory cannot survive in Git, so a new
repository cannot select the documented nested shape without an unrelated placeholder, a separate
directory-creation step, or remembering `--out aplan/tasks` on its first write. Later writes then
follow whatever that first command happened to create, making layout an accidental first-run
decision.

The adopter used `--out aplan/tasks`, so this caused no data loss. The question is whether a starter
configuration should make the default deterministic, not whether the escape hatch works.

## What to decide

- Whether `init` should declare an explicit output directory, scaffold a trackable plan directory,
  or `add` should choose `<root>/tasks` for a new default-root plan even before it exists.
- How an existing root-flat plan keeps its current placement without a surprise migration.
- What the first-plan documentation and dry-run say so layout is a visible choice rather than an
  inference from an empty directory.

## Acceptance criteria

- [ ] a newly initialized repository gets a deterministic documented first-task location without
      relying on an empty directory Git cannot preserve
- [ ] an existing root-flat plan continues to add beside its tasks unless it explicitly migrates
- [ ] tests cover init plus first single add and first batch add for both supported layouts
- [ ] dry-run and help name the selected output directory before anything is written
