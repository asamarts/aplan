## Why

The workflow ergonomics increment has three lanes: completion history, terminal Markdown rendering
and the capture inbox. Each lane crosses storage, human output and machine surfaces. Unit-complete
pieces can still disagree on provenance, raw output, atomicity or TUI parity. Stable product
qualification needs an adversarial end-to-end verdict over the assembled increment; repository
visibility does not waive it.

## Acceptance criteria

- [ ] fresh and legacy fixture repositories complete CLI, JSON, MCP-resource/tool and TUI journeys
      for all three lanes
- [ ] command, option, MCP tool/resource, TUI, schema, semantic-renderer and Markdown-output
      censuses each enumerate and drive new members
- [ ] malicious terminal text, malformed storage, shallow Git and interrupted multi-file writes
      fail safely
- [ ] performance budgets cover large histories, large Markdown bodies/tables and large inboxes;
      pagination stays snapshot-consistent and no task-count-times-history scan survives
- [ ] protocol-version tests distinguish domain collection pages from MCP catalogue pages,
      preserve legacy-client compatibility and keep mutable repository resources private and
      immediately stale
- [ ] dependency, license, MSRV, binary-size, terminal portability and accessibility audits pass or
      own exceptions
- [ ] docs distinguish exact fact, inference and unknown; human rendering, raw source and
      artifacts; capture and task
- [ ] retry tests prove capture source-key and promotion idempotency across a lost response, while
      conflicting retries and stale previews fail without partial writes
- [ ] upgrade guidance covers old done tasks, existing `show --body` consumers and
      repository/config discovery
- [ ] every finding is fixed, filed in the owning product cut or declined with recorded evidence
