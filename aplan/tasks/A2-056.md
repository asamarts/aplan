## Why

An adopting repository authored a live task whose `paths` named `tests/test_runner.py`, a file
that did not exist (the real file was elsewhere). `show`, `check` and `verify` all passed; the
mistake surfaced only when the delivery tried to run that file. `paths` are ownership and
evidence scope, so a typo there weakens every later `commit` citation.

A todo task may legitimately name a file it will create, and `APLAN053` already reports an
`in_progress` task whose paths match nothing tracked. The open question is whether an exact
(non-glob) path on a live task deserves a note or warning earlier, and how that interacts with
files a task will create. Related: A2-091 (one live path hiding dead siblings) and A2-099 (a
catch-all claim failing late). A2-101 already plans an early diagnostic that tells a literal path
that disappeared from a prospective glob, so this decision is sequenced in front of it, in the
same cut.

## Acceptance criteria

- [x] a decision is recorded on whether and when an exact live path that matches no tracked file is
      reported, consistent with `APLAN053`, A2-091 and A2-099 (`ADR-0071`, `HLD.md`)
- [x] if a change is chosen, an implementation task is filed with its criteria (`A2-101` updated to
      cover both stranded historical literal paths and bare tracked directories per `ADR-0071`)

## Why it is `untestable`

This task records the design decision in `ADR-0071` and updates `HLD.md` and `A2-101`; no executable
product behaviour changes until `A2-101` implements it with regression tests.
