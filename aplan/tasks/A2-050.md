## Why

Reported in #30. A trace anchor can match both a heading and a table row; the heading wins.
When that heading is renamed, the same anchor silently resolves to the row instead. `check`
passes and `verify` reports only an ordinary `APLAN045` section change, which a repository
may run as advisory. Deleting the row as well produces the `APLAN008` error a rename should
have produced, so the row hides the error.

Options from the report, in its order of preference: (1) record the element kind in the
stamp and say when an anchor now resolves to a different kind; (2) lint an anchor that
matches both a heading and a row when it is written; (3) document the precedence and the
consequence. The two codes it touches differ. The case #30 reports is `APLAN045` on an open
task, which stores no stamp: its baseline is the commit that last touched the task file, so the
element kind at that commit can be recomputed from history. `APLAN018`'s stored stamp is a bare
content hash, so recording the kind there changes what a stamp holds. That needs a decision before
code.

## Acceptance criteria

- [x] a decision is recorded (ADR or HLD section) choosing among the options, with the consequence
      for `APLAN045` and for the `APLAN018` stamp spelled out separately (`ADR-0069`, `HLD.md`)
- [x] the implementation task's criteria are updated to the decision, or it is dropped with the reason

## Why it is `untestable`

This task records the design decision in `ADR-0069` and updates `HLD.md` and `A2-051`; no executable
