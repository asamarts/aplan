## Why

`evidence.require_min_strength` is a **set of acceptable kinds**. The name says *minimum
strength*, which reads as a floor on an ordering, and an adopter who reads it that way writes the
opposite of what they mean.

One adopting repository did. It set `[file]` intending "a path that exists is the floor; anything
stronger is welcome", and got a policy that accepts **only** `file` and refuses `commit`, which
`verify` resolves against the task's own `paths` and which is unambiguously the stronger citation.
Measured by swapping one closed task's citation:

```
$ # ABC-001: `file: docs/streams/example/plan.md` replaced by `commit: <sha>`
$ aplan check
error[APLAN017] ABC-001: `done` but no evidence of a required kind (need one of: file)
```

The diagnostic is correct and even prints the set. What it cannot say is that the author asked for
the wrong thing, and the consequence compounds: with `[file]` in force, the only citation that
closes a task is a path, so the adoption cited each work stream's own archived plan document for
**61 of 91** citations. A policy meant to raise the bar had pinned it to the weakest kind in the
vocabulary, and `docs/upgrading.md`'s guidance ("start at `[commit, test, file]` ... and narrow to
`[test]`") reads as a progression along an ordering, which is exactly the reading that produces
`[file]` as a starting point.

Three ways out, and the first is nearly free:

1. **Rename it.** `evidence.accept_kinds` says what it does. The old key stays as an alias for a
   release, which `version.*` already makes expressible.
2. **Refuse the degenerate case.** `[file]` alone is almost always a mistake; a warning naming the
   kinds it excludes would have caught this on the first run.
3. **Make it an actual floor**, ordered `test > commit > file > note`, so `[file]` means what every
   adopter will read it to mean. Biggest change, and it removes the ability to demand `test` while
   refusing `commit`, which some plan may want.

## Acceptance criteria

- [ ] the key's name or its documentation makes the set-versus-floor reading unambiguous before a
      plan is written against it
- [ ] a policy that accepts `file` and refuses `commit` is either reported or made impossible
- [ ] `docs/upgrading.md`'s progression row says it is a set, since its own wording is what reads
      as an ordering
