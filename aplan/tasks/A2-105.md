## Why

ADR-0029 deliberately keeps one plan inside one repository, so an upstream task in another
repository cannot be a graph edge. Two adopting repositories have now paid the consequence. One
invented a local milestone plus a risk note for a freeze in a sibling repository. The other parked
a CI task on prose naming an upstream aplan task (an installable release for CI); that work had
already shipped, but the sentence and its distant revisit date left the local gate parked for
weeks.

The model decision stands. What is missing is a named adoption recipe that says which facts are
local and checkable, which remote id is only context, and how soon the prose must be re-read.

The first of those adopters later made that recipe executable rather than hypothetical. Its local
proxy can check a terminal task in the sibling repository's plan from a clean detached checkout,
by pinning a revision, running `check` and `verify`, then inspecting structured `show` output. The
proxy can still remain stale, which is why `A2-123` decides whether the product should resolve the
condition directly. Until that decision, this task owns the fail-closed manual route rather than a
vague instruction to "check the other repository".

## Acceptance criteria

- [ ] adoption guidance gives one canonical encoding for a cross-repository blocker: a local
      task or milestone owns the dependency, a risk/body line names the remote work, and a dated
      revisit owns reconciliation
- [ ] the recipe states that the remote id is prose rather than a resolved edge and that its
      status must not be copied as a local status claim
- [ ] both examples above (a freeze in a sibling repository, and a wait on an upstream tool
      release) are representable without reopening ADR-0029 or implying aplan verifies the
      sibling repository
- [ ] the guidance points at `due` for revisits and at URL evidence only for a claim whose remote
      checker can actually resolve it
- [ ] the executable recipe pins an immutable sibling revision, uses trusted local configuration,
      runs that plan's `check` and `verify`, inspects typed task status, and treats unavailable,
      unverified or moved input as still blocked
- [ ] the revisit interval is deliberately short and the local proxy records the observation before
      a person performs the ordinary local transition; no copied remote status is presented as a
      live automatically verified edge

## Why it is `untestable`

This task records an adoption recipe for a deliberately unsupported cross-repository relationship.
A test can assert that prose exists, but cannot prove the recipe is understood or that another
repository re-reads its remote blocker.
