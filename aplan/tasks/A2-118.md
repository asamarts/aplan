## Why

The server currently hand-authors input schemas and carries JSON as text. The new completion and
inbox workflows need richer collection reads, but adding a tool for each presentation would
contradict the bounded MCP tool rule (broad and alternate read views, including every rollup, are
not tools; see the Agents section of `HLD.md`) and make agents parse prose or consume unbounded
context. MCP already provides declared output schemas, structured content and URI-addressed
resources; aplan needs one versioned transport boundary before those workflows extend it.

Build on the shared application boundary's concrete typed requests and identified inputs. The
current MCP revision also changed lifecycle, result envelopes and cache metadata, while aplan must
keep serving clients on its documented older revision. This is not permission to create a
universal request map, daemon, subscription service or parallel domain model.

## Acceptance criteria

- [x] MCP input and output schemas are generated from the concrete typed application requests and
      responses, declare an explicit contract version and are checked as derived artifacts
- [x] every existing tool has generated input/output schemas and returns schema-conforming
      object-enveloped `structuredContent` plus concise text; if the SDK blocks a member, a held
      failing comparison keeps this task open rather than making partial migration look complete
- [x] tests fail if structured and text views name a different subject, verdict or semantic
      effect
- [x] identified, bounded resources/templates cover at least one existing focused read and one
      collection view, with stable URI semantics, documented size limits and no whole-plan dump
- [x] a small typed page component carries order, limit, completeness and an opaque continuation
      bound to input identity plus request; changed inputs or arguments refuse a stale
      continuation
- [x] application collection pages are not confused with protocol pagination of tool/resource
      catalogues; resource-template URIs carry domain continuations explicitly and canonically
- [x] the executable MCP audit classifies and drives every CLI command, tool, resource and
      template, preserving the bounded tool rule rather than asserting unused table entries
- [x] tool results expose denial and semantic effects; resource results expose input identity and
      completeness; neither requires parsing the human compatibility text
- [x] malformed arguments, output-schema drift, oversized results, stale continuations, unknown
      resources and older text-only client behavior are covered end to end
- [x] a protocol compatibility matrix covers the currently supported handshake-era revision and
      `2026-07-28`: result envelopes, object-only legacy structured content, discovery/lifecycle,
      resource errors and required cache metadata are either proved or explicitly version-gated
- [x] changing repository resources advertise private, zero-freshness cache semantics; cursors are
      size-bounded, strictly parsed and cannot broaden a selector even when modified by a client
- [x] security review covers schema validation, output sanitization, URI/path confinement,
      resource and work/result bounds plus advisories in the enabled SDK feature graph, while
      adding no repository-controlled executable extension point
- [x] the locked SDK is retained when it can satisfy the matrix; any upgrade is measured for MSRV,
      features, advisories and wire compatibility rather than assumed from current upstream docs
- [x] server identity/facts, README, HLD, changelog and upgrading guidance state the contract
      version and compatibility rules; a changed existing behavior receives a `Behaviour` and
      proof
