## Why

One adopting repository closed a task with the identical `file:deny.toml` citation twice. `close`
accepted and stored both, `verify` resolved both, and no check reported that one explicit edit had
gone wrong. The duplicate does not weaken the verdict, but it falsely inflates the visible evidence
list and is the same signal defect that `APLAN040` already catches for repeated path entries.

The write surfaces can refuse a duplicate before storing it. Existing files still need a
diagnostic, because direct edits and older builds can already have written the state.

## Acceptance criteria

- [x] `close` and every `amend` form refuse an exact duplicate evidence citation before writing,
      naming the kind and reference already present
- [x] `check` reports duplicate citations already on disk while `verify` continues to resolve the
      distinct set rather than multiplying work or counts
- [x] equality is defined over kind plus canonical reference; two different kinds naming the same
      text and two genuinely distinct references remain allowed
- [x] zero, one, two and three copies are tested, including non-adjacent copies and more than one
      duplicate family in a task
- [x] the rule's message and agent instruction distinguish harmless duplication from unresolved or
      weak evidence, with the required unit and end-to-end scenario coverage
