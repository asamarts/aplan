## Why

The CLI already has the capture inbox and atomic promotion of a capture into an ordinary task
(ADR-0063). Agents need the same low-friction intake path, but guidance must not encourage them to
file a weak capture when they already have enough information for a proper task. Broad reads must
also remain resources under the existing MCP policy, and mutations cannot bypass lifecycle,
policy, retry or atomic promotion gates.

## Acceptance criteria

- [ ] bounded inbox and focused-capture resources expose the same typed read results with input
      identity, limits, completeness and input-bound continuations; list/show are not rollup tools
- [ ] capture and promote are admitted as tools only if the executable MCP command policy
      (`MCP_COMMAND_POLICY` and its census) proves their bounded actions; amend/discard remain
      human operations unless separately justified by that rule
- [ ] the executable MCP surface census drives every resource, template, tool and deliberate
      CLI-only disposition
- [ ] declared output schemas match `structuredContent` and concise compatibility text without
      forcing agents to parse prose or duplicating domain response types
- [ ] resource URIs, cache hints and continuations follow A2-118's current/legacy protocol matrix;
      mutable private inbox data is never advertised as shared or fresh
- [ ] validation, warning policy, atomic refusal, timestamps, source-key retry and promotion
      idempotency match the shared application layer
- [ ] generated agent guidance explains when to capture, when to add a task and how promotion
      works
- [ ] agent export remains generated from configured capability text rather than hand-edited
      drift
- [ ] schemas and tests cover malformed arguments, stale continuations, unavailable inbox,
      concurrent writes, lost-response retries and conflicting repeat promotion
