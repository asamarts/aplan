## Why

An adopting repository recorded a task's first delivery commit while the task remained
`in_progress`. When the second increment landed, `close` refused because an `evidence` block already
existed and pointed to `amend`; `amend` refused because the task was not `done`. The file was
structurally valid, no rule reported it, and deleting evidence by hand was the only supported
escape.

Generic reproducer: `ABC-001` is `in_progress` with `evidence: [{kind: commit, ref: 1111111}]`.
`aplan close ABC-001 --evidence commit:2222222` refuses and names `amend`; `aplan amend ABC-001
--add-evidence commit:2222222` refuses because the task is not done.

Partial evidence on live work is a coherent claim: it says some proof exists, not that the task is
complete. The close transaction should judge the complete final evidence set rather than require
that set to have been empty before the transaction began.

A second adopter reproduced the same boundary after deliberately attaching seven citations so
hosted CI could execute only that task's current evidence before closure. Removing and recreating
the block was safe but introduced a manual window in precisely the bounded-evidence workflow the
citations enabled. The final transaction must support that case without weakening or duplicating
proof.

## Acceptance criteria

- [x] closing a `todo` or `in_progress` task preserves its existing citations, combines them with
      citations supplied by the close request, resolves the complete final set and writes `done`
      plus every required fingerprint atomically
- [x] an adequate existing set may close without a redundant citation, while invalid, duplicate,
      ambiguous, stale or too-weak existing evidence refuses without changing status or evidence
- [x] conflict and recovery output names a command that actually accepts the task's current status;
      it never points from `close` to an `amend` form that is guaranteed to refuse
- [x] already-done tasks retain their guarded amendment boundary, and milestones, dropped tasks,
      unchecked mode, repository warning policy and concurrent source changes keep their current
      fail-closed semantics
- [x] CLI, application and MCP callers share one typed close transaction; tests cover zero, one and
      many existing citations, new citations after the existing one, both live statuses, late
      resolution failure, fingerprint drift and a stale snapshot
- [x] the widening of `close` earns a proved `Behaviour`, and help, HLD, changelog, upgrade guidance
      and facts explain that existing evidence is evidence to validate rather than a dead end
