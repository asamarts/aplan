## Why

The Action verifies a release's SLSA provenance with `gh attestation verify --signer-workflow ...
--source-ref ... --deny-self-hosted-runners`. It checks only that `gh` is on `PATH`, not which
version it is. Hosted runners ship a current `gh`; a self-hosted runner may carry an old distro
package.

- Below gh 2.68.0, `--source-ref` does not exist and verification fails with an unknown-flag
  error. That is safe, because it fails closed, but the message does not say that the fix is to
  upgrade `gh`.
- From 2.68.0 up to, but not including, 2.102.0, verification runs with weaker matching than the
  flags promise. `--signer-workflow` matched only the start of the certificate identity and
  `--source-ref` compared case-insensitively until 2.102.0, and regex metacharacters in
  `--signer-workflow` went unescaped until 2.97.0. 2.102.0 also fixed a symlink issue in
  `gh release download`, which the install step uses.

Exploiting the matcher weaknesses against this Action needs an attestation signed inside
`asamarts/aplan` itself, so the practical risk is low. Still, the Action's promise is that it
executes only a release that `release.yml` built for the exact tag, and that promise should not
depend on the runner's `gh` version without saying so. Reported alongside #36; `A2-028`
documents the prerequisites.

## Acceptance criteria

- [ ] the install step reads `gh --version` and refuses below 2.68.0 with a message naming the
      installed and required versions and saying that no plan check ran
- [ ] between 2.68.0 and 2.102.0 the step warns, naming the fixed matcher weaknesses and the
      recommended version, or refuses if the maintainer decides the weaker matching is not
      acceptable; the choice is recorded in the task and the README
- [ ] the version comparison is tested against representative `gh --version` outputs, and the
      Action self-test still passes on hosted runners
