## Why

An adversarial audit in an adopting repository produced four new citations for one already-closed
task: the corrective source commit, an evidence commit, a report and the exact regression test.
`aplan amend --add-evidence` resolved and wrote each citation correctly, but the flag accepts only
one value. Repeating it is a Clap refusal, so the adopter needed four separately loaded, resolved
and published mutations to express one known post-state.

```console
$ aplan amend ABC-001 --add-evidence commit:1111111 --add-evidence test:suite::regression
```

Observed: a Clap refusal of the repeated flag. Expected: one atomic amendment adding both.

The task-creation surface is not the right owner: it governs task-creation fields and explicitly
keeps evidence-bearing terminal state behind the ordinary evidence gate. This is an existing
closed-task repair transaction. It also is not only an `add` arity tweak: once a caller can state
several evidence changes, additions, removals and replacements need one deterministic conflict
model, one input snapshot, one evidence-resolution decision and one guarded publication. Otherwise
a failed later citation can leave an earlier repair published, which is the opposite of the
atomicity the batch is meant to buy.

The implementation should reuse the typed, evidence-gated amendment boundary that the close,
amend and restamp workflows already expose to interactive clients, rather than add a CLI-only
mini-engine.

## Acceptance criteria

- [ ] `amend` accepts repeated add, remove and replacement operations in one invocation while the
      existing one-operation forms remain compatible; help and errors show the repeatable grammar
- [ ] the batch has simultaneous, deterministic semantics: every removal/replacement source is
      judged against the original task, duplicate/conflicting operations are refused by name, and
      argument grouping or ordering cannot silently change the final evidence set
- [ ] every introduced citation is parsed and resolved through the ordinary amendment evidence
      gate, the final task is checked under repository warning policy, and any invalid operation,
      stale input or publication failure writes none of the batch
- [ ] evidence fingerprints for retained, removed and newly introduced file citations match the
      final set; `--no-resolve` reports exactly which checks were skipped once for the whole batch
- [ ] CLI and shared application callers use one typed repair transaction and one guarded write;
      the result reports every semantic change without reparsing human prose
- [ ] adversarial tests cover several valid additions, mixed operations, one invalid citation late
      in a batch, repeated/conflicting sources and targets, existing task defects, warning-policy
      differences, drift fingerprints and a source snapshot race
