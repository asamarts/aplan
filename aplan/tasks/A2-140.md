## Why

One adopting repository pins aplan behind a checked-in launcher script. That launcher
authenticates the binary and its complete facts contract before delegating any plan read or
mutation, so a bare `aplan` found on `PATH` is deliberately non-authoritative. `export-agents-md`
nonetheless hard-codes bare `aplan` in every generated command and in the prose naming the gate and
MCP server. The repository must keep a hand-written preamble that reinterprets the generated block,
which is exactly the second policy copy the generator exists to remove.

A second adopter reproduced the write-side consequence: its generated loop used bare commands, so
a newer `PATH` build performed a valid dependency edit and also rewrote the contract block away
from the pinned gate's bytes. A repository launcher would have kept reads, mutations and contract
generation on the same authenticated build.

This is not a request to discover a binary or trust an environment variable. The repository must
declare the invocation as ordered argv, the generator must render it safely and deterministically,
and the ordinary default must remain byte-for-byte unchanged. A wrapper may itself take fixed
arguments, so one opaque executable-path string is not sufficient.

## Acceptance criteria

- [x] repository configuration can declare one non-empty generated-agent invocation as ordered,
      non-empty argv; defaults still mean the single token `aplan`, and malformed, blank or
      ambiguous values fail configuration rather than falling back
- [x] every executable aplan example and executable-identifying sentence in the generated block
      uses one deterministic shell-safe rendering of that argv, without evaluating shell syntax,
      changing plan semantics or altering the configured process used by the current command
- [x] changing the invocation changes generated bytes and `--check` reports the stale contract;
      default configuration reproduces the pre-feature generated block byte-for-byte
- [x] the config key and a named argv-safety behaviour appear in `facts` and work through
      `facts --require`, so pinned consumers can require the capability before generating policy
- [x] command-driven tests cover a path with spaces, fixed launcher arguments, quotes, control
      characters and option-looking tokens; generated Markdown remains bounded, fenced correctly,
      non-executable as data, and idempotent across `--write` then `--check`
- [x] the configuration reference, upgrade compatibility table and changelog explain the default,
      the trust boundary and migration for repositories that previously carried a hand-written
      launcher reinterpretation
