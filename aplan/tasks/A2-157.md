## Why

While authoring a task in an adopting repository, `aplan add --paths 'src/**,docs/**,tests/**'`
accepted the comma-separated argument as one literal path. `check` also accepted that syntactically
legal but practically dead claim, so the task appeared to own three surfaces while its one matcher
owned none. Repeating `--paths` produced the intended list, but the singular metavar and absence of
a diagnostic made the wrong form plausible and silent.

## Acceptance criteria

- [ ] `add` help and diagnostics state one unambiguous way to supply several paths, consistent with
      the parser's actual repeat/value semantics.
- [ ] separator-shaped path arguments that strongly indicate an attempted list fail before mutation
      with the corrected repeated syntax; legitimate path syntax retains an explicit escape if
      commas remain valid repository filename characters.
- [ ] CLI and application tests cover repeated paths, the comma-separated near miss, one legitimate
      comma-bearing path if supported, no file written on refusal, and the exact post-state path
      list.
- [ ] README and changelog document the chosen compatibility boundary without teaching a second
      list syntax.
