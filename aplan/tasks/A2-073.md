## Why

In one adopting repository, three tasks written from files cost three rejected runs, all on one
field:

```
unknown field `effort_days`, expected one of `title`, `id`, `phase`, `cut`, `effort`, ...
```

The input key is `effort`; the stored key, the one `aplan show` prints and every task file on disk
carries, is `effort_days`. An adopter's first `--from` file is most likely copied from an existing
task, and **an existing task cannot be fed back in**.

`manifest.rs`'s own doc comment says the entry shape is "the frontmatter contract, not a
translation". For this one field it is a translation, and nothing says so. That is the defect
rather than the rejection: the error message is good, naming the field, the position and the
accepted set, which is what let the second attempt happen without opening documentation.

The adopter left it as upstream's call whether input/output key symmetry is worth an alias. The
call should be recorded either way.

## What to decide

**Whether `effort_days` is accepted as an alias.** Cheap (`#[serde(alias = "effort_days")]`) and it
makes the round trip work. The cost is two spellings for one field, and `deny_unknown_fields` is
there precisely so a misspelled `efort` is refused rather than silently dropping 153 estimates: an
alias narrows that net by one name that is not a misspelling.

**Or whether the input key should simply *be* `effort_days`**, making the comment true and the
round trip work, at the cost of breaking every `--from` file already written against `effort`. The
adopters that used this seam are known (one authored 134 tasks through it), so the blast radius is
measurable rather than hypothetical.

The second finding in the same report (that neither accepts `1d` while `--effort`'s own help reads
in days) is a separate question about a duration vocabulary and is not in scope here.

## Reproduced from the task-file direction

The same adopter hit the same field mismatch again while filing one task from a copied task-file
shape. It first supplied a single mapping, because `add --from` help did not say the top level is a
YAML sequence, then changed that and was refused on `effort_days`. The runtime diagnostic for both
mistakes is unusually good; the author should not need to fail once to learn the document's outer
shape or fail twice to learn that its fields are not the stored ones. This strengthens the
round-trip defect here and adds the missing help criterion.

## Acceptance criteria

- [ ] a task file this tool wrote can be used as an `add --from` entry without editing a field
      name, or the reason it cannot is stated where the shape is defined
- [ ] whichever is chosen, `manifest.rs`'s claim that the shape is "not a translation" is true or
      corrected
- [ ] a misspelled field is still refused, shown by a test
- [ ] `add --from` help states that the document is a sequence of task mappings and names the input
      versus stored-field boundary before an author discovers it from a refusal
