## Why

ADR-0054, HLD section 5.5, `docs/upgrading.md`, and `TestRunner::timeout_seconds` all specify that
`test.timeout_seconds` bounds test discovery (`test.list` and `test.skipped`) while test execution
(`test.run`, `test.batch.run`, and the miss sentinel) remains deliberately unbounded by it so the
test framework or batch adapter owns execution timeouts.

In `crates/aplan-evidence/src/resolve.rs`, sharing `configured.command_policy()` across discovery
and execution caused `execute_once`, `execute_batch_as`, and `run_sentinel` to pass
`limits.timeout_or(0)` to `spawn_capped`. When a runner sets an explicit non-zero
`test.timeout_seconds` for discovery and a test or batch runs longer under `aplan verify
--execute`, `spawn_capped` kills it and `execute_once` / `execute_batch_as` panic on
`Ok(Ran::TimedOut(_)) => unreachable!(...)`, while `run_sentinel` silently drops its probe.

## Acceptance criteria

- [x] `test.run`, `test.batch.run`, and the miss sentinel clear `timeout_seconds` from
      `CommandPolicy` while preserving `max_memory`, `max_processes`, `max_output`, and `wrap`
- [x] discovery commands (`test.list` and `test.skipped`) continue to enforce
      `test.timeout_seconds` (default 600s, `0` disables)
- [x] `execute_once` and `execute_batch_as` replace `unreachable!` with structured non-panicking
      timeout handling (`APLAN014`, `CitationOutcome::TimedOut`, `TestBatchOutcome::TimedOut`)
- [x] named behaviour `verify.test_timeout_bounds_discovery_only` and regression tests cover
      single-test, miss-sentinel, and batch execution under a short `test.timeout_seconds`,
      discovery timeout enforcement, and structured timeout handling
