## Why

The `A2-009` parser switch refuses files v0.6.0 read. Probed on 2026-11-18 with the v0.6.0
release binary and a build of `main`:

| input | v0.6.0 | `main` |
|---|---|---|
| task `title: !!timestamp 2026-01-01` | reads the string | `APLAN001` "invalid type: enum" |
| task `title: !!binary aGVsbG8=` | reads the string | `APLAN001` |
| task `title: !<tag:example.com,2000:x> hello` | reads the string | `APLAN001` |
| task declaring `%TAG ! tag:example.com,2000:` and writing `title: !x hello` | reads | `APLAN001` |
| KEP `creation-date: !!timestamp 2024-01-15` | imports | refused, naming serde internals |
| KEP `kep-number: !!timestamp 2024-01-15` | imports as `KEP-2024-01-15` | refused |
| capture `title: !!timestamp 2024-01-15` | listed | `APLAN057` |

These read the same in both: a `%TAG` directive that no value uses, core tags on plain scalars
(`!!str hello`, `!!int 2`) and a local tag such as `!local hello`, which both refuse.

`ayaml` keeps a tag outside YAML's core schema on a generic value, where the bridge dropped it
and kept the scalar. The front-matter, capture and KEP reads then refuse it; the configuration
reads that keep a generic value do not, and still read `!!timestamp`. That is a regression for an
adopter whose files use one, however rare.

The switch also accepts what v0.6.0 refused: a core tag on a quoted scalar, such as
`effort_days: !!int "2"`, `!!float "2.5"`, `phase: !!int "1"` or `owner: !!null ""`, now reads
as the tag says. YAML defines that reading, so it is a divergence to record rather than undo, but
the CHANGELOG and `docs/design/yaml-parser.md` say core tags read as before and that nothing is
newly accepted, and they name KEP as the one product read that keeps a generic value; config and
`close` keep one too.

**Decision (2026-11-18).** Every product read goes through one rule, in `aplan_core::yaml`, that
reads tags as the bridge did: a global tag is dropped, a scalar beneath it reads as its text where
the target takes any value and as the type a typed target asks for, and a local tag is refused
where the target cannot keep it, with an error that now names it. The reads of task files,
`.aplan.yml`, KEPs and `add --from` manifests use it over the compatibility reader. Captures,
blueprints and dependency manifests keep the strict reader and its refusals; a document it parses
that carries a tag is then read under the rule, and every other document, a refused one included,
reads exactly as before. A core tag keeps the meaning YAML gives it on every field: on a quoted
scalar it stays accepted, and one that contradicts a typed field (`!!str 30` for a number) stays
refused, though the bridge's typed read ignored it. Copying either would copy a quirk of the bridge
rather than a rule. Two readings `ayaml` 0.1.3 settles before the rule sees the tag stay as they
are, pinned by tests: a number, boolean or struct beneath a tag in YAML's own namespace that is not
a core one (`!!timestamp`) is refused, and `~` beneath any other global tag is null to a unit
target. No aplan format has a use for either, and a task's numbers meet its schema first.

## Acceptance criteria

- [ ] each row above reads in `main` as it does in v0.6.0, or a recorded decision says which
      stay refused, with an error that names the tag and the field rather than an enum
- [ ] a local tag stays refused, with an error that names it and the field
- [ ] the hostile-input differential pins `!!timestamp`, `!!binary`, a non-core verbatim tag and
      a declared `%TAG` handle as read, a local tag as refused, and the quoted core tags as a
      known divergence, each with its reason
- [ ] the CHANGELOG entry for `A2-009` and `docs/design/yaml-parser.md` describe the result, and
      no longer claim core tags read as before, that nothing is newly accepted, or that KEP is
      the one read keeping a generic value
