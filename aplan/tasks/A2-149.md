## Why

`require_effort` and APLAN009 require an estimate but do not bound it. An adopting repository's
8.0-day task passed every gate even after repeated increments showed that it was a container rather
than one reviewable unit. A universal number would be false precision, so the repository must
declare its own limit and the diagnostic must point to the decomposition primitive from A2-148.

## Acceptance criteria

- [x] configuration declares an optional positive maximum for live non-milestone task effort, with
      an explicit disabled posture, schema validation and generated documentation
- [x] a stable rule reports the task's measured effort, configured limit and supported decomposition
      action; exactly-at-limit is accepted and over-limit is refused under repository policy
- [x] milestones, dropped tasks and repositories that do not opt in remain silent; missing, zero,
      negative, infinite and non-numeric estimates retain or strengthen their existing refusals
- [x] add, batch add, import and every typed interactive/MCP creation path judge the same proposed
      post-state before writing, while loading an existing oversized task yields the same rule
- [x] tests cover boundary values, fractional values, disabled and malformed configuration,
      decomposition rollups, migrated legacy plans and stable human/JSON/agent instructions
- [x] rule catalogue, README, HLD, upgrade guide and changelog explain that the limit is a local
      review-size policy, not a duration forecast or a universal productivity claim
