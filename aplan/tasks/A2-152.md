## Why

An agent in an adopting repository claimed and started two tasks, then closed both with evidence.
Three hours later `aplan show` still described each terminal task as held by the closer. `close`
neither released the local ephemeral claim nor mentioned it, so every linked worktree displayed
finished work as active until somebody independently ran `aplan release` twice.

ADR-0051 deliberately made claim durability `local_ephemeral_until_explicit_release` so a clock
never guesses that live work stopped. A terminal task is different evidence: the same operation
has just recorded that work ended. The correction must reconcile those truths without letting one
actor silently clear another actor's coordination record or pretending that a plan-file write and
the separate Git-common claim store can be one atomic publication.

The same repository found three adjacent defects on the claim surface:

- **The mirror case on a live task.** A task left `in_progress` with no claim on it (never taken,
  or since released) shows `ready yes` with no holder, and `aplan ready` lists it like a `todo`
  one. The committed status says someone is working on it, and the claim store says nobody holds
  it. `show` and the task collections should report that disagreement too, not only a stale claim
  on a terminal task.
- **A refusal worded as corruption.** Refusing to take a claim somebody else holds reports
  `invalid local claim state at .../claims-v1.json` (`ClaimError::Invalid`), the wording for a
  damaged file, before it names the holder and `--from`. A refusal should read as one.
- **Raw epoch times.** Every claim time prints as raw Unix seconds ("claim recorded at Unix time
  N", "held by `...` since Unix time N"). An agent resuming after its context was compacted had to
  run `date -d @N` to learn how old its own claim was. Human output should add a UTC timestamp and
  an age, and machine output should keep the integer.

## Acceptance criteria

- [x] a new ADR revisits only ADR-0051's terminal-transition lifecycle and decides when a successful
      close releases, retains or marks a claim stale, including same/different/unknown identity,
      takeover races, unavailable or unsafe claim stores and dropped tasks
- [x] CLI, MCP and TUI close use one typed application outcome: a same-actor claim is cleaned up
      according to the decision and reported; another actor's claim is never silently removed and
      is reported with safe recovery guidance
- [x] a plan closure remains truthful if coordination cleanup fails after publication: the command
      reports the partial local cleanup instead of rolling back or calling the whole close absent,
      and an idempotent retry can complete the cleanup
- [x] `show`, task collections and interactive inspectors distinguish an active live-task claim
      from a terminal-task stale claim left by an older build or failed cleanup; machine output
      retains the complete record and does not authenticate the holder label
- [x] an `in_progress` task with no claim is not presented as fresh ready work: human, JSON, MCP
      and TUI surfaces name the status/coordination disagreement and its safe recovery
- [x] a valid claim held by another identity is an ordinary typed refusal, never corruption of the
      claim store; the message names the holder and the exact takeover or release operation
- [x] human claim times include an absolute UTC instant and a stable age while machine output
      retains the epoch value; boundary tests cover a new claim, an old claim and clock skew
- [x] linked-worktree and concurrent tests cover close by the claimant, close by another identity,
      takeover/release races, cleanup failure and a legacy terminal claim across CLI/MCP/TUI parity
- [x] the existing explicit-release/no-timeout guarantees remain intact for live work, and the
      changed behavior has a proved capability name, release note and upgrade/recovery guidance
