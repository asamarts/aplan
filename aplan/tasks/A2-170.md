## Why

An MCP client that writes its requests and then closes the server's standard input loses the
replies to any request still running. Reproduced on 2026-11-18 with both the v0.6.0 release
binary and a build of `main`: `initialize`, a `tools/call` of `aplan_verify` (id 7) and a
`tools/call` of `aplan_show` (id 9) were written and stdin was closed. The server answered ids 1
and 9, never answered 7, and exited 0 with nothing on stderr. `serve` returns as soon as the stdio
transport reports end of input, which drops the handlers still in flight.

A scripted client, a test harness or an agent runtime that pipes a batch and closes the pipe
cannot tell a lost reply from a hung server, and a silent exit 0 says everything went well.

## Acceptance criteria

- [ ] on end of input the server finishes every request it has already read and writes each
      reply before it exits, within a stated bound
- [ ] a test writes a slow request and a fast one, closes stdin at once, and receives both replies
