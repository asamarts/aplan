## Why

An adopting repository saw the MCP `aplan_add` tool refuse four schema-valid additions, in
two separate sessions, with `the plan changed while aplan_add was preparing its batch;
nothing was written; run aplan_add again`. The worktree was clean, nothing else edited the
plan, and the CLI `aplan add` succeeded immediately against the same checkout. The refusal
was safely atomic, but its only prescribed recovery is the retry that kept failing, and it
does not say which observed plan identity disagreed.

## Acceptance criteria

- [ ] the compare-and-swap mismatch is reproduced in a test, and its cause is fixed so that an
      unchanged plan is not reported as changed
- [ ] a genuine concurrent change is still refused atomically
- [ ] the refusal names what differed (for example the two snapshot digests), so a persistent mismatch
      is distinguishable from a race
