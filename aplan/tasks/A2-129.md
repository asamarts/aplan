## Why

The runner guidance correctly says that one runner sees one feature set, but then recommends one
runner per feature set without stating the overlap boundary. One adopter's Go integration build tag
showed the common counterexample: the tagged listing is a superset of the untagged listing, so two
runners make every ordinary test ambiguous under `APLAN013`. One runner carrying the tag lists and
runs both sets without weakening citation identity.

Another adopter showed the distinct case that must remain documented: a default-feature runner can
itself prove disabled-feature behavior, while a narrowly targeted feature runner owns unique
integration tests. The correct advice depends on whether the listings overlap and whether the two
configurations prove materially different claims, not merely on the number of feature sets.

## Acceptance criteria

- [ ] runner documentation says that `list` and `run` may carry build tags or feature flags and
      must describe the same executable test universe
- [ ] guidance prefers one superset runner when a tagged listing includes every untagged name and
      the same invocation can run both, avoiding duplicate-name ambiguity
- [ ] guidance preserves separate runners when configurations prove distinct behavior, and shows
      that their listings must be narrowed to unique names
- [ ] README guidance, scaffold/schema documentation and upgrading guidance give the same rule
