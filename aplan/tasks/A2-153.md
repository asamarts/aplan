## Why

In an adopting repository, a change rewrote parts of two files that two closed tasks cite as
`file:` evidence. Run before the commit, `aplan verify` reported `0 warning(s), evidence resolved`,
and so did the repository's gate. Both read the fingerprints at `HEAD`, which did not hold the
change yet. Once the change was pushed, CI's plan stage printed `APLAN054` for both citations. The
finding is advisory, so the run passed, and nobody read it until `verify` ran by hand to close the
task. This project's pre-public plan hit the same sequence: verify, commit, push, then a fresh audit
reported `APLAN054`. There it was handled as procedure.

Running the checks and then committing is the natural order, and an adopter's pre-commit habit
or editor integration does exactly that. `verify` already holds each file citation's
fingerprint. It can tell, without a commit, that the working tree's bytes for a cited file
differ from the stamp, and so that the result it prints is about `HEAD`, not about what is
about to be committed.

A second adopter found the same temporal blind spot in `APLAN045`. A review changed traced sections
without touching fourteen open tasks. `check` and `verify` were green before the commit; the
pre-push run on the identical committed bytes then reported the tasks because history finally gave
the document edit a time. A short external script predicted every subject from `HEAD`, the working
tree, traces and task paths, so the information is already local. Fourteen no-op "re-read, holds"
notes were needed only to make task history newer than the future document commit.

## Acceptance criteria

- [x] when a cited file differs in the working tree from its stamp, `verify` reports the citation,
      task and prospective `APLAN054` beside the unchanged `HEAD` verdict
- [x] when a traced section differs from `HEAD` and an open task carrying that trace is untouched,
      the candidate projection reports the prospective `APLAN045`; it handles one and many tasks,
      row anchors and section boundaries without requiring a synthetic task edit
- [x] staged, unstaged, deleted and unchanged inputs are distinguished, and a clean working tree
      prints nothing new; only cited files, traced documents and their task files are read
- [x] advisory projection does not change the current-tree verdict or exit status, and human,
      JSON, agent and MCP output carry the same typed candidate facts without calling them resolved
- [x] tests commit the candidate bytes as a control and prove the predicted subjects and rule codes
      equal the subsequent clean-HEAD result, including a task whose text genuinely needs updating
      and one whose no-op re-read would only satisfy history ordering
- [x] the changed meaning of `verify` has one proved behaviour name, release note and upgrade
      guidance; documentation distinguishes current evidence resolution from candidate projection
