## Why

The release transaction proves one exact source, validates it, builds inside an immutable native
environment, and publishes a checksum. The checksum detects changed bytes only after a consumer
has obtained an authentic digest. Nothing a consumer can verify currently binds the archive digest
to the public repository, the protected release workflow, or the exact hosted build invocation.

GitHub artifact attestations can close that gap without storing a signing key. A short-lived OIDC
identity obtains a Sigstore certificate, and an in-toto statement binds the archive digest to the
workflow and source. The attestation must be part of the existing same-job transaction: after the
validated reproducible build, before any registry package or GitHub asset is published, and
verified before publication can proceed.

## Acceptance criteria

- [x] an ADR states the subject, signer identity, verification policy, rerun semantics, and the
      boundary between build provenance, release approval, checksums, and reproducibility
- [x] the protected release job uses the current GitHub-owned attestation action pinned to one
      reviewed full commit and grants only the OIDC and attestation permissions it requires
- [x] the one release archive is attested after exact-source validation and construction, then
      verified against `asamarts/aplan` and `.github/workflows/release.yml` before any publication
- [x] manual release staging exercises attestation and verification without publishing crates or
      release assets; a failed, skipped, or weakly scoped verification cannot reach publication
- [x] executable tests audit the action pin, permissions, single-subject path, workflow ordering,
      tag-only publication boundary, exact verifier arguments, and zero/many archive neighbours
- [x] consumer and maintainer documentation gives the exact online verification command without
      claiming that the previously published v0.5.2 archive has an attestation
- [x] change-aware and complete validation pass, followed by a successful protected hosted staging
      run that creates and verifies an attestation from the integrated source

## Rollout record

PR <https://github.com/asamarts/aplan/pull/12> received an independent approval and rebase-merged
the implementation as `b459892cd80e8ec372efbbfd7d8cdf12cb7a1ff6`. Its final hosted run
<https://github.com/asamarts/aplan/actions/runs/41880269586> passed Linux development validation,
Windows 2025 portability and macOS 15 portability on the identical reviewed tree. PR
<https://github.com/asamarts/aplan/pull/11> was superseded without a source change after GitHub
left a macOS job pending even though all of its steps, including job completion, had succeeded.

The local complete profile passed all 11 gates with 3,626 tests, all 12 crate coverage floors and
whole-plan verification of 14 tasks with zero warnings. Protected manual staging run
<https://github.com/asamarts/aplan/actions/runs/41883649583> then passed the same complete profile,
built the archive from the exact integrated commit and created build provenance for SHA-256
`c2bb2196836af424c4ecc78b57571d932b8dfcadfbbf8ff74286193ff658d0da`.

GitHub stores the attestation at
<https://github.com/asamarts/aplan/attestations/63708190>, and its signature is recorded in the
Rekor transparency log at <https://search.sigstore.dev?logIndex=3691593992>. The repository API
returns exactly one attestation for that digest. The checked-in verifier accepted the bundle only
after matching the repository, release workflow, source commit and `refs/heads/main`, SLSA
provenance predicate, GitHub Actions OIDC issuer and GitHub-hosted runner. The crates.io and GitHub
release steps were skipped because staging ran on `main`; previously published v0.5.2 remains
deliberately un-attested.
