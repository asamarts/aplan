## Why

An adopter typed the flat-looking form of a dependency edit. In a plan with `ABC-001` and
`ABC-002`:

```console
$ aplan dep ABC-002 --after ABC-001
```

Clap correctly refuses it, because the edit is `aplan dep add ABC-002 --after ABC-001`, but the
failure prints only `Usage: aplan dep [OPTIONS] <COMMAND>`, and a second `--help` invocation is
needed to discover `add` and `rm`. `tag` has the same nested shape and the same error. Root-command
errors can suggest a nearby command; nested parents should not become a less informative
exception. Expected: the same failure names the parent's child commands and a copyable valid form.

Fix the command tree rather than hand-writing one `dep` sentence. The available choices already
exist in Clap's model and must drive errors for every current and future nested command.

## Acceptance criteria

- [ ] a missing or unrecognized child of every nested command lists that parent's available child
      commands in the same failure, without requiring a second `--help`
- [ ] the audit enumerates nested parents and children from Clap's command tree, so a new nested
      command cannot silently retain the old placeholder-only usage
- [ ] `dep ABC-002 --after ABC-001`, `dep bogus`, `tag bogus` and a near-match each retain exit 2,
      preserve useful Clap context and point at a copyable valid form
- [ ] errors wrap within the established terminal width, remain deterministic and color-safe on
      stderr, and do not duplicate a hand-maintained command vocabulary
- [ ] valid invocations, root-level usage and machine-readable command output are unchanged
- [ ] the widened diagnostic behavior of the existing nested commands is named and proved if it is
      not already assertable through the CLI surface registry
