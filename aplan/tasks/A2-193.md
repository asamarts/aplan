## Why

Filed by `A2-081` (`ADR-0068`). A repository can currently verify its binary only through an
external wrapper script or after strict `.aplan.yml` deserialization fails with an `unknown key`
error. `ADR-0068` decides a narrow, pre-schema `requires` block in `.aplan.yml` (`min_version`,
`capabilities`, `source`, `facts_sha256`) evaluated before full `Config` deserialization across
CLI, MCP, and TUI, while keeping exact executable digest pinning (`binary_sha256` / SLSA
attestation) at the external wrapper/Action boundary.

## Acceptance criteria

- [x] `aplan-config` implements a frozen pre-schema `requires` reader (ignoring unrelated top-level
      keys while strictly validating `requires` sub-keys `min_version`, `capabilities`, `source`,
      and `facts_sha256`) that runs before full `Config` `deny_unknown_fields` deserialization
- [x] `requires.min_version` accepts bare released `X.Y.Z` versions only, refusing pre-release
      strings (such as `0.8.0-dev`) as vacuous pins and directing authors to `capabilities`,
      `source`, or `facts_sha256`, while evaluating running pre-release builds with standard SemVer
      precedence (`0.8.0-dev` satisfies `0.7.0`, not `0.8.0`)
- [x] `Config` and derived `schemas/v1/config.json` declare `requires` with `min_version`,
      `capabilities`, `source`, and `facts_sha256`, and deliberately exclude `binary_sha256`
- [x] CLI, MCP, and TUI fail closed (exit 2 / refusal) on a build-contract mismatch, naming both
      the declared requirement and the running build's `version`, `source` (or `unknown`), and
      `facts_sha256`, before reporting unknown config keys introduced after the build
- [x] `requires.source` fails closed when the running build's `source` is absent/unknown and admits
      same-source rebuilds with different binary bytes without claiming reproducibility
- [x] `aplan facts`, `aplan facts --identity`, `aplan facts --require`, `aplan --version`,
      `aplan schema`, and `--no-config` remain reachable when `requires` refuses the running build
- [x] executable old/new/same-version/headless/unknown-source fixtures prove mismatch diagnostics
      against injected `ToolIdentity` and `BuildFacts` values rather than self-checking only the
      running binary
- [x] `facts.json`, `schemas/v1/config.json`, `docs/upgrading.md`, `HLD.md`, and `CHANGELOG.md`
      are updated and passing `xtask gen-schema --check`, `docs::`, and `mcp_parity::`
