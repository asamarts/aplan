## Why

Two adopting repositories have hit the same skew from opposite directions: one wrote `ratified_by`
against a `0.3.0` binary, and another's first command failed because a machine-wide installed
`0.3.0` could not read aplan's own `.aplan.yml` (`version.current`).

The diagnostic is already as good as a message gets: it names the running version, counts the keys
it accepts, points at `docs/upgrading.md`, and explains that a newer key reads exactly like a typo
from an older binary. Nothing about the text needs changing.

What it cannot do is fire before the adopter has installed the wrong thing. The open question is
whether a plan should be able to declare the build contract it needs (a version floor, exact
identity, required capabilities/schema, or some combination) that the loader can diagnose before it
validates ordinary keys. Filed because declining it would be a claim about how many adopters run a
stale machine-wide binary, which one repository cannot see.

## Cases the decision must cover

**Displacement among pinned development builds.** One adopter recorded repeated displacement among
legitimate project-pinned development builds on one shared machine. Its local wrapper compares
version and digest before invoking aplan, but the plan itself cannot state that expectation.
Another adopter showed that the release, Action and staging install path is no longer the missing
part: it pins a staged binary by digest in CI. The remaining question is precisely this task's
required-build declaration and first-command diagnostic, not distribution.

**Same version text, different builds.** One plan was written by one `0.5.0-dev` build and rejected
by an older build printing the identical version after `close` added `evidence_fingerprints`.
`aplan facts --identity` already supplies the nearby exact-build answer; version text alone cannot
be the declaration or remedy.

**Upgrading is not "install newer".** One adopter's pinned gate was clean while a newer `PATH` build
added three warnings. A safe upgrade has to identify the candidate, compare capabilities and rules,
run it against the current plan, disposition newly introduced findings, then move the authoritative
pin. Otherwise an old build silently checks less, or a new build becomes authoritative because it
happened to be first on `PATH`. A2-122 separately owns generated-block oscillation; this task owns
how the repository chooses the build in the first place.

**Same source, different binaries.** One adopter observed two different binary digests built from
the same source commit while the facts digest stayed fixed. Source identity bounds semantic review,
but it is not exact artifact identity unless the build is reproducible and that claim is itself
checked. Any accepted contract must say whether it pins a distributed artifact digest, requires a
reproducible-build attestation, or deliberately treats same-source rebuilds as equivalent; it may
not silently conflate them. The same adopter then saw the complementary case inside one work
session: both the source revision and binary digest changed while the facts digest did not, and its
repository wrapper refused the new build until the operator re-reviewed it. That wrapper is
load-bearing, but the plan still cannot declare or explain the exact-build requirement on its first
command.

**The operational cost of an old pinned build.** One adopter ran mutations through a pinned `0.4.0`
build while current builds already attribute only newly introduced findings to a mutation. Five
pre-existing broken traces blocked unrelated writes in the pinned build. That is the cost of a
repository being unable to state which behaviour set its plan requires, not a reason to weaken
trace validation.

## Acceptance criteria

- [x] an ADR decides among semantic-version floor, exact identity, required capability/schema set,
      or an explicit combination, accounting for released and same-version development builds
      (`ADR-0068`)
- [x] an exact-identity design distinguishes source revision, facts digest and binary digest, and
      states how same-source rebuilds are admitted or refused without assuming reproducibility
      (`ADR-0068`)
- [x] the decision states what can be read before the ordinary configuration schema, how an older
      binary reacts to a declaration it cannot parse, and why the result cannot become a
      green-by-construction self-check (`ADR-0068`)
- [x] `docs/upgrading.md` gives one staged upgrade procedure: identify both builds, compare the
      relevant facts, run the candidate on the unchanged plan, disposition new findings, then move
      the authoritative pin before adopting new keys or generated output
- [x] unknown config/frontmatter fields direct same-version development users to
      `aplan facts --identity` where the running build supports it, without claiming an old binary
      can diagnose a capability invented after it (`docs/upgrading.md`, runtime update tracked in
      `A2-194`)
- [x] if a declaration is accepted, file implementation, schema, compatibility and diagnostic
      tasks with executable old/new-build fixtures; if it is rejected, document the exact wrapper
      contract adopters must enforce instead (`A2-193`, `A2-194`, plus external artifact wrapper
      contract in `ADR-0068` and `docs/upgrading.md`)

## Why it is `untestable`

This task records the compatibility model and upgrade procedure. Follow-up implementation tests can
prove an accepted declaration, but cannot prove the version-versus-capability tradeoff itself; a
rejected design leaves documentation rather than executable product behaviour.
