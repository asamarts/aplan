## Why

One adopting repository supplied `cut: M-ci` to `add --from` and received `ABC-056`, inside a
milestone whose other members are all `XYZ-nnn`. Nothing was misconfigured: the plan has one
global id convention and declares no relationship between a cut and an id family. `check` stayed
green on a mismatch that makes the milestone's membership look wrong to a reader.

Some plans use prefixes only as opaque ids, so the relationship cannot be inferred. A plan that
does use prefixes as a second copy of cut membership needs to declare that vocabulary once and
have both minting and validation read it.

A second adopter reproduced the authoring half without an invalid result: a phase-0 task placed in
`M-zero` was minted as `QR-084` even though that cut's work uses `P0-nnn`. Both families are legal
and the task's phase and membership are correct. The missing piece is still an optional cut
declaration, not a global heuristic and not an assumption that every prefix encodes membership.
Supplying a full `--id` remains the one-off escape; it does not let a batch or agent ask the plan
which family to use.

The first adopter then supplied the stronger ambiguous case. Its `M-mixed` cut already contained
six `XYZ-nnn` tasks and one `ABC-nnn` task; `add --from` minted `ABC-091`, while `XYZ-008` would
have been equally defensible. Better inference cannot resolve a mixed cut without guessing. The
declaration must therefore be authoritative when present, and the no-declaration behavior must
remain explicit and deterministic rather than pretending that membership reveals intent.

A later batch from the same adopter supplied explicit `DEF-nnn` ids inside another mixed-family
cut and confirmed the complementary boundary: per-entry `id:` already gives a knowledgeable author
a deterministic escape. The cut declaration requested here is therefore a default for authors and
agents that do not already know the family, not a second id-assignment mechanism and not a reason
to override an explicit id silently.

The same adopter reproduced the default a fourth time while dry-running trace anchors:
`--cut M-ci` still proposed `ABC-107`. The real seventeen-task batch avoided the mismatch only by
supplying every `XYZ-nnn` id explicitly. This strengthens the need for one declared default but
does not change the ambiguity or the explicit-id escape above.

A third adopter adds the case a per-cut declaration does not reach: a task tagged `cross-cutting`
belongs to no cut, so a CI task added without `phase` was minted `P8-002`, in the family of the
plan's last phase, where all of that plan's CI work is `P0-nnn`. A plan also needs a declared
default family for a task outside every cut.

## Acceptance criteria

- [x] a plan can optionally declare the id prefix or id strategy associated with a cut without
      changing plans that treat ids as opaque
- [x] `add` and `add --from` mint from that declaration when no explicit id is supplied
- [x] a plan can declare one default family for work with no cut, including `cross-cutting`
      tasks; it is used only when neither an explicit id nor a cut-specific declaration applies
- [x] an explicit id that contradicts the declared cut family is reported with both values and an
      actionable repair
- [x] ambiguous, overlapping and changed mappings are rejected or migrated deliberately rather
      than resolved by iteration order
- [x] help states which input selects an id family and points one-off authors at explicit `--id`,
      without claiming phase or cut affects plans that made no declaration
- [x] schema, facts, rule coverage, configuration docs and upgrading guidance ship together
