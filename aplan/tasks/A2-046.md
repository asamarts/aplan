## Why

Reported in #22. One edit to a broadly traced section reports every closed task that traces
it (`APLAN018`), and the fix, `close --restamp`, takes one id, so the repair becomes a shell
loop that is not atomic. A follow-up on #22 reports the same for `APLAN054`: one edit changed the
file evidence of two closed tasks, and each needed its own `close --restamp`, which refreshes
trace and evidence stamps alike. A restamp is also meant to record that someone re-read the
section for each task, and a batch form makes that per-task judgement cheaper to skip: the cost
ADR-0015 describes, where a warning that is always correct to dismiss trains dismissal. The
report proposes one guarded write for several ids, all or none, with evidence flags staying
single-id.

Untestable: a decision record.

## Acceptance criteria

- [ ] a decision is recorded on a multi-id restamp, weighing atomic repair against per-task review
- [ ] the implementation task's criteria match it, or it is dropped with the reason
