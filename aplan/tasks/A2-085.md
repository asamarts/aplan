## Why

`anchor::headings` recognises setext headings, and a document's closing `---` reads as one: the
last line of any `---`-fenced metadata block becomes an h2. One adopting repository carries front
matter on every plan document, so this mints a phantom anchor in 107 of its 113 plan documents,
and a second one in those that carry a nested metadata block. The shape, in `docs/plan.md`:

```
---
id: ABC
...
public_readable: false     <- anchor `public_readable-false`, h2
---                        <- read as the setext underline
```

The adopter measured this against the real binary rather than inferring it. A task `ABC-001`
tracing `docs/plan.md#public_readable-false` passes `aplan check` with zero warnings, while the
same task tracing `docs/plan.md#no-such-heading-at-all` gets `APLAN008` naming the file. So the
phantom resolves, and the only thing standing between an author and a trace anchored to metadata
is that `#public_readable-false` does not look like a section anybody would cite.

Two consequences, and the second is the sharper one:

1. GitHub does not render front matter, so this anchor does not exist in the document a reader
   sees. An anchor that resolves in the tool and not in the artifact is the inverse of an earlier,
   since-fixed defect, where a heading written as a link minted an anchor GitHub does not, and the
   tool refused an anchor a reader could copy from the rendered page.
2. `APLAN018` fingerprints the traced section, bounded by heading level. A fingerprint on a
   front-matter phantom covers the metadata, and metadata is the part of a plan document that
   changes most (`last_updated`, `last_verified`, `status`). In the adopter's layout the phantom's
   section happens to end at the next line, but the layout is the author's choice: a document
   whose front matter ends with `last_updated` would register a drift every time a date was
   touched.

CommonMark says a setext underline follows a *paragraph*, and the line above a closing `---` inside
a `---`-fenced block is not one. The narrow fix is to skip a leading front-matter block the way the
task loader already does, and to treat a `key: value` line under a `---` as metadata rather than a
heading; the wider one is to decide whether `resolvable_anchors` should offer anything a reader
cannot see in the rendered document.

## Acceptance criteria

- [x] a document's leading front-matter block mints no heading anchor
- [x] a nested `---`-fenced metadata block in the body does not either, or the decision to keep it
      is recorded
- [x] a test pins both, using a front matter whose last key is a date, which is the case that would
      have registered false drift
- [x] `docs/rule-catalogue.md`'s `APLAN008` entry says what is and is not an anchor in a document
      that carries front matter
