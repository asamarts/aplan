## Why

`aplan roadmap --format markdown` writes one table per cut, and a markdown table is sized by a
renderer to its own content. So the sections of `ROADMAP.status.md` do not share a column width:
measured across it when this was filed, the title column ran 39 to 78 characters and the evidence
column 85 to 253. Read on a forge, adjacent tables of visibly different widths look ragged.

The human format does not have this: `roadmap_human` computes one id width across every member of
every cut, and says why: "so the rows of one report line up with each other rather than each cut
inventing its own column". That was a deliberate fix. The markdown surface never had the equivalent
because markdown has no column widths to set.

**Why this is deferred rather than done.** The obvious fix does not work and the working fix costs
something real:

- **Padding the source cells changes nothing a reader sees.** Each section is a separate table, and
  a renderer sizes each to its own content whatever the source bytes are. Padding helps only someone
  reading the raw file.
- **Padding also churns the diff.** This file is drift-gated and reviewed as a diff. Padded to a
  global width, one long title anywhere re-pads every row in the document, and with a 253-character
  evidence column every row becomes roughly 400 characters. Refusing "a diff nobody asked for" is
  the argument this project already settled when `dep add` stopped reformatting a `blocked_by` list
  that `mv` would have left alone.
- **The only fix that actually aligns the rendered output is one table** of every row (359 when this
  was measured) with a `cut` column. That trades away the per-cut headings, which are the document's
  navigation and its organising idea. A roadmap grouped by cut is the point of it.

So the question is a genuine trade, not a defect: uniform width against grouping. It was raised,
considered, and deferred with the reasoning written down rather than re-derived later.

## Acceptance criteria

- [ ] a decision on whether uniform rendered width is worth losing the per-cut sections for, with
      the reasoning recorded where the next reader of the document will find it
- [ ] if it is: one table, a `cut` column, and the per-cut rollups kept somewhere a reader still
      reaches them
- [ ] if it is not: the trade is recorded so the observation does not come back as a bug report
- [ ] whichever way, `ROADMAP.status.md` stays byte-identical to what `gen-roadmap` writes, so the
      drift gate still means what it says
