## Why

`prefer_after` ranks without blocking (ADR-0025). `APLAN033` validates its entries (an unknown id
is an error), and a milestone id passes that check, because a milestone is a task in the model. It
then has no effect whatsoever.

Measured in an adopting repository: same task, same command, only the reference type differs (the
ids here are generic):

```
prefer_after: [ABC-001]     check exit 0    ABC-020 ranks #4 of 22
prefer_after: [M-one]       check exit 0    ABC-020 ranks #1 of 22
(no prefer_after)           check exit 0    ABC-020 ranks #1 of 22
```

The milestone form is indistinguishable from writing nothing. The adopter added it to all 18 members
of three cuts, got `ok: 74 tasks`, and got the same `ready` order it started with.

## Why it matters more than one inert field

The case it cannot express is the common one. That adopter wanted "phase-2, -3 and -4 work ranks
below phase-1 work", which is a statement about cuts, and the only mechanism that expresses it is a
milestone `blocked_by` edge, which *blocks*, and therefore also lengthens the critical path and
removes the work from `ready`. Those are the two corruptions ADR-0025 was written to avoid: writing
those edges "would corrupt `ready` (it would stop offering the work), `critical-path` (it would
lengthen a chain that does not exist)".

So a plan wanting a discretionary order over a cut has to choose between a hard edge that overstates
and a field that silently does nothing. The adopter took the hard edge, deliberately, and wrote down
that it was overstating.

Expressing it task by task is the other option, and it is the one ADR-0013 exists to remove: that
ADR replaced 81 hand-written edges with 7 milestone ones for the blocking case. `prefer_after` has no
equivalent.

## Acceptance criteria

- [ ] `prefer_after` naming a cut either ranks every member of that cut, or is refused with a
      message saying it cannot be done and what to write instead
- [ ] whichever it is, silence is not among the outcomes: a plan that asks for something this tool
      will not do hears so from `check`
- [ ] the decision is recorded against ADR-0025, which added the field and did not say whether its
      entries may be cuts
- [ ] the changed meaning or refusal of the existing `prefer_after` field has one proved behaviour
      name, release note and upgrade statement

## Notes

Found by an adopting repository while choosing how to stop `ready` offering phase-4 work during a
phase-1 MVP.

`APLAN033`'s own summary is "a `prefer_after` entry names a task that can actually be preferred". A
milestone is precisely a task that cannot actually be preferred, so the rule's wording already
describes the case it does not catch.

A second adopting repository reproduced the same need across five new cuts. The intended order was
partly graph truth and partly priority judgement, so prose became a second ungated copy. This task
owns the latter without turning it into a dependency.
