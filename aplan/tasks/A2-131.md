## Why

`export-agents-md` tells an agent that the narrowest matching policy scope wins, but omits the
second half of the validator's rule: among equally narrow matches, the first entry in the file
wins. The scoped-policy design required both precedence halves to be stated, and the
configuration reference already says so; the generated contract does not.

One adopting repository has exactly that shape, with two one-tag scopes matching the same tasks.
A generic reproducer:

```yaml
# .aplan.yml
policy:
  - when:
      tag: [bootstrap]
    evidence:
      require_min_strength: [commit]
  - when:
      tag: [build]
    evidence:
      require_min_strength: [test]
```

A task `ABC-001` tagged `bootstrap` and `build` is judged by the first scope. The generated block
prints both requirements, each saying that the narrowest matching scope wins and that the line is
one of them, without enough information to determine which applies to `ABC-001`.

## Acceptance criteria

- [ ] Generated agent guidance states that the first configured scope wins when matching scopes
      name the same number of dimensions.
- [ ] A regression fixture uses one task matched by two equal-specificity scopes and proves the
      generated explanation identifies the same winner as validation.
- [ ] Reversing the two scopes reverses the documented winner and the validator result together;
      whole-plan and unequal-specificity wording remains exact.
- [ ] User-facing policy documentation and the changelog describe the complete precedence rule
      without requiring a reader to inspect implementation code.
